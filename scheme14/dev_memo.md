## 0. この文書の使い方（最初に読むこと）

**この文書は進捗メモではなく、設計の連続性そのものである。**

開発は複数日にまたがるが、各日の作業者は前日の記憶を持たない。
したがって「なぜその設計にしたか」が、着手時に読む範囲に無ければ、翌日の作業者は
平気で別の判断をする。それは scheme12 が抱えた「複数の書き手が少しずつ違う
判断をした結果、層が積み重なった状態」を、一人で再生産することを意味する。

### 作業開始時

1. **§1 設計憲章と §2 凍結仕様を必ず読む。** ここは原則として変更しない。
2. §6「まだ破りやすいこと」を読む。決定の全文は開かない。
3. §7「現在の状態」で、どこまで動いているかを把握する。
4. §8「次にやること」を見る。未解決は §9。利用者判断、または利用者の手元でしかできないと書いてある項目は、指示があるまで始めない。

### 作業終了時

1. 憲章・凍結仕様・アーキテクチャに効く決定は、その節へ短い規則として書く。却下した案は1文で足す。
2. その日の経緯の全文は [log/decisions.md](log/decisions.md) の末尾「続報」へ追記する。37日目までの本文は動かさない。却下した案も書く。§6 の索引には1行足すだけにする。
3. §7 は事実だけを現状に合わせる。数が変わったらその数を書き換える。日ごとの段落は足さない。
4. §8 には未着手だけを残す。終えた手順は消す。記録はログにある。
5. §9 には未解決だけを残す。解けた問いは消す。

### 憲章を変えたくなったら

変えてよい。ただし **節の中の規則と、ログのその日の節の両方に、何をなぜ変えたかを残す。**
黙って変えるのが最も避けたい行動。変える前に、ログの該当する決定を開く。

## 1. 設計憲章（不変の決定）

この節に「scheme13」とあるのは、書き直したときの名前である。いまこの憲章を守るのは scheme14 で、編集するのは `scheme14/` だけである。

**scheme14 の目的。** scheme13 は scheme12 を一貫した設計で作り直した処理系である。成果は設計の統一に加え、SICP のプログラムが動くことと、そのために入った浮動小数点数である。scheme14 は実装を減らさず、開発メモだけを継続できる大きさに戻した。メモを短くするために、この成果を外さない。

### 1.1 目的

scheme12 は機能的には完成しているが、複数の書き手の判断が層として積み重なり、
以下のような構造的な澱みが残っている。scheme13 はこれを設計として解消する。

- `Op::LDCT` — コンパイラが一度も生成しない命令が VM に残っている
- `Op::LD` / `Op::LSET` にフレームのベクタ表現とリスト表現が両方生きている
  （「後方互換：リスト形式もサポート」）。最もホットなコードに死んだ分岐がある
- `Op::ARGS` が引数をリストに固め、`APP` が即座にベクタへ戻す（三重変換）
- 文字列型が二重（Scheme 値は `GcString`、シンボル名や `Instruction::sym` は
  `std::string`）で、後者が `GC_MALLOC_UNCOLLECTABLE` からリークする
- `write_newline`（旧API）が `newline` と併存
- ソース中に `// ... (expand_let, ... は以前と同じなので省略)` という
  AI 生成時の足場が残っている

**scheme13 の目的は「新機能」ではなく「同じ振る舞いを、選び直した設計で実現する」
こと。** 機能追加の誘惑に負けないこと。

### 1.2 環境と依存

| 項目 | 決定 |
| --- | --- |
| 開発環境 | Windows（w64devkit / MinGW の g++ と GNU make）。ビルドは `make -C scheme14`。Dev Container は scheme13 までの環境で、scheme14 では使わない |
| 言語 | C++17 |
| GC | Boehm GC（`gc.h` / `gc_cpp.h` / `gc_allocator.h`、`-lgc -lgccpp`） |
| 多倍長整数 | Boost.Multiprecision `cpp_int` |
| これ以外の依存 | **増やさない** |

**理由**: scheme14 の作業環境は利用者が Windows に決めた（2026-10-01。経緯はログの続報）。
言語・GC・多倍長は動かしていない。自前 GC や自前 bignum はこのプロジェクトの主題ではない。

### 1.3 ファイル構成

**単一ファイルとする。分割しない。** scheme14 では `scheme14/scheme14.cpp`。
`scheme13/scheme13.cpp` は保存してある前の版で、ここでは直さない。

**理由**: 利用者はこのファイルを単体で AI に渡してレビュー・改修を依頼する
運用をしている。分割するとその運用が壊れる。また既存の Makefile 群が
単一ソースを前提にしている。そもそも scheme12 の問題はファイル数ではなく
「退役させなかった決定が層になったこと」であり、分割は解決策ではない。

代わりに **セクション構造を厳格に守る**（§3 参照）。

**却下案**: `value.hpp` / `reader.cpp` / `compiler.cpp` / `vm.cpp` への分割。
上記の運用上の理由により却下。

### 1.4 三つの優先順位（利用者と合意済み）

1. **既存 `.scm` 資産との互換性が最優先。**
   `system_lib.scm` / `mlib7.scm` / `hashtable_lib.scm` /
   `rbtree_lib_improved.scm` と各テストが**一字も変えずに動く**ことが絶対条件。
   Common Lisp 由来の表面仕様（§2）はそのまま引き継ぐ。R5RS 準拠のために
   表面を変えることはしない。

2. **性能を明示的な設計目標に含める。**
   scheme12 は約 30 万呼び出し/秒。呼び出し規約を最初から設計し直す（§4）。
   これは後から変えにくい部分なので、やるなら最初にやる。

3. **ソース位置つきエラーを実装する。**
   リーダが行・列を記録し、コンパイル時・実行時エラーに位置を添える。
   デバッグ処理系としての価値が最も上がる部分。
   当初は `error` と `dynamic-wind` と `with-exception-handler` を入れないと決めた。
   8日目の決定41で `error`（見出しを出して止まる）を足し、13日目の決定58・59で
   多値と `dynamic-wind` を足した。2026-10-07 に、ライブラリが `error` を呼んでも
   呼び出し元が `with-exception-handler` で受けて、外側から続行できるようにした。
   ハンドラが無いときは、今までどおり見出しを出して止まる。経緯はログ。

### 1.5 デバッグ機能は一級市民

`trace-on` / `trace-off` / `compile` / `disassemble` / `globals` / `macros` /
`help` はこの処理系の看板。後付けではなく最初から設計に組み込む。
特に逆アセンブル表示は、命令セットを変えるたびに追随させること。

### 1.6 GC の規律（scheme12 の失敗から）

scheme12 では以下のバグが実際に起きた。同じ轍を踏まないため規律として固定する。

1. **GC ヒープ上のオブジェクトが後始末を要するなら、必ずファイナライザを
   登録する。** `gc` 継承だけではデストラクタが呼ばれない。
   （scheme12 の `FilePort` がこれでディスクリプタを枯渇させた）
   scheme13 では `gc_cleanup` の多重継承ではなく、`make_port()` の中で
   `GC_REGISTER_FINALIZER_IGNORE_SELF` を明示的に呼ぶ形にした（理由は
   [`log/decisions.md`](log/decisions.md) の3日目・決定13）。**ポートを作る経路は `make_port()` ただ一つに限ること。**
2. **GC オブジェクトが持つ文字列は必ず `GcString`**
   （`std::basic_string<char, ..., gc_allocator<char>>`）にする。
   `std::string` を持たせると、`gc` 継承クラスのデストラクタが呼ばれないため
   `GC_MALLOC_UNCOLLECTABLE` から確保されたバッファが永久に解放されない。
   （scheme12 の `Symbol::name` / `Instruction::sym` / `Closure::params` が該当）
3. **GC オブジェクトが持つコンテナは `gc_allocator`、GC 管理外のルート
   （グローバル表など）は `traceable_allocator`** を使う。
4. `cpp_int` の limb 配列は `gc_allocator<unsigned long long>` を渡し、
   `GC_DECLARE_PTRFREE(unsigned long long)` を宣言する（保守的 GC の
   偽 retention を防ぐ）。scheme12 の該当コードは正しいので踏襲する。
5. **ファイルを開く関数は `EMFILE`/`ENFILE` で `GC_gcollect()` +
   `GC_invoke_finalizers()` してから1回リトライする。**
   `GC_gcollect()` だけではファイナライザがキューに積まれるだけで実行されない。

### 2.2 型と述語

- **文字型は存在しない。文字は長さ1の文字列。**
  `(string-ref "abc" 1)` → `"b"`、`(integer->char 65)` → `"A"`
- `eq?` と `eqv?` は同一実装。**数値は値比較**（`(eq? 100000000000 100000000000)`
  → `TRUE`）、シンボルは名前比較、文字列はポインタ比較（`(eq? "a" "a")` → `FALSE`）
- **正確な整数と、不正確な実数の2種類**（18日目に改訂。決定81）。
  整数は即値 fixnum とヒープ Bignum、実数は IEEE 754 の倍精度（binary64）。
  **有理数と複素数は無い。** `(/ 7 2)` が `7/2` になることはない（決定82）
- `eqv?` は**正確さが一致して初めて真**（決定86）。上の「数値は値比較」は
  **同じ正確さどうしの話**で、そこは1つも変わらない。
  `(= 1 1.0)` → `TRUE` だが `(eqv? 1 1.0)` → `FALSE`。
  実数どうしの `eqv?` はビット列で比べるので `(eqv? 0.0 -0.0)` → `FALSE`、
  `(eqv? +nan.0 +nan.0)` → `TRUE`（`=` のほうは逆に `TRUE` / `FALSE`）
- 実数の結果は**整数に落とさない**。`(* 2.0 3.0)` は `6.0` であって `6` ではない
  （決定85。整数側の「表現をひとつに正規化する」規律と**向きが逆**。§6 の「正規化する」を読むこと）

### 2.3 算術

- `(/ -7 2)` → `-3`（0方向への切り捨て。`quotient` 相当）。
  **引数がすべて正確な整数のときの `/` は今までどおり**（18日目に利用者が選択。決定82）
- `(/ x)` は**エラー**:
  `/ requires at least 2 arguments (single-argument reciprocal is not supported; use (/ 1 x) instead)`
  **引数の型によらずエラー**。`(/ 2.0)` も同じ（型で arity を変えない）
- `(modulo -7 2)` → `1`、`(modulo 7 -2)` → `-1`（符号は除数に一致）
- 多倍長: `(* 99999999999 99999999999)` → `9999999999800000000001`

**実数が混ざったとき（18日目に追加）**

- **伝播規則: 引数に不正確な数が1つでもあれば、結果も不正確**（決定91）。
  `(+ 1 1.5)` → `2.5`、`(/ 7 2.0)` → `3.5`、`(* 2 3.0)` → `6.0`
- `(/ 1 3)` → **`0`**。SICP のような実数前提のコードは `(/ 1.0 3)` あるいは
  `(exact->inexact ...)` と書く。**これは仕様であって不具合ではない**（決定82）
- 比較（`=` `<` `>` `<=` `>=`）に NaN が混ざったら**どの比較も偽**（決定87）。
  `(< +nan.0 1)` も `(>= +nan.0 1)` も `FALSE`。
  **`>=` を「`<` の否定」で書かないこと**
- 整数と実数の比較は整数を倍精度に寄せる。**2^53 を超える整数では桁が落ちる**
  （決定88。正確に比べるには有理数が要るので、そこは入れない）
- **整数を要求する場所は実数を受け取らない**（決定92）。添字・長さ・文字コード・
  `modulo` / `quotient` / `remainder` / `even?` / `odd?` はすべて
  `wrong type of argument` + `expected: an integer` で弾く。`(vector-ref v 1.0)` はエラー
- 0除算: `(/ 1 0)` はエラーのまま。`(/ 1.0 0.0)` は `+inf.0`
  （**実数の除算は IEEE 754 に従い、例外にしない**）

### 2.5 構文

- **角括弧 `[` `]` は区切り文字ではない。** `'[1 2]` は `[1` と `2]` という
  2つのシンボルとして読まれる（結果として `unbound global: 2]`）
- `#t` / `#f` と `true` / `false` / `nil` のリテラルを両方受け付ける
- `,@` は内部的に `splice` というシンボルに読まれる
  （`unquote-splicing` ではない）
- 準クオートはネストする。カンマは同じ深さのバッククオートだけを打ち消す。`(let ((x 'foo)) `(a `(b ,,x)))` は `(a (quasiquote (b (unquote foo))))`。表示は略記にしない
- `define-macro` によるマクロのみ。`syntax-rules` はない
- 実数のリテラル（18日目に追加。決定89）。**トークン全体が形に一致したときだけ数**で、
  外れたものは今までどおりシンボルになる
  - `1.5` `-0.75` `.5` `1.` `1e10` `1.5e-3` `+2.5E7`
  - `+inf.0` / `-inf.0` / `+nan.0` / `-nan.0`（R7RS の綴り）
  - `1/2` `1.2.3` `1e` は**シンボル**（有理数は無い。§2.2）
  - ドット対とは衝突しない。`.` がドットになるのは次が区切り文字のときだけなので、
    `(a .5)` は `a` と `0.5` の2要素、`(a . 5)` はドット対

### 2.6 内部 define

本体**先頭**の連続した `define` のみ `letrec` に変換される。
式より後ろの `define`、マクロが生成した `define`、本体先頭の
`(begin (define ...) ...)` のスプライスは**グローバル定義になる**（scheme12 と同じ）。

### 2.7 継続

- `call/cc` と `call-with-current-continuation` の両方を受け付ける
- `call/cc` と `apply` は**特殊形式であって値ではない**。
  `(procedure? call/cc)` → `FALSE`
- トップレベルのフォームは個別に評価されるため、フォームを跨いで継続を
  起動すると、そのフォームの残りは実行されず次のフォームへ進む

## 3. ソースのセクション構造

「とりあえず近くに」置かない。** 該当セクションがなければセクションごと作る。

```

 4. 表示                 to_string / display / write、循環検出
 5. リーダ               トークナイザ、S式パーサ（位置を記録する）
 6. 構文検査             syntax_error / check_arity / check_bindings

 8. コンパイラ           命令生成、環境解決、内部 define の scan out
 9. 命令セット           Op と Instruction、逆アセンブル表示
10. VM                   実行ループ、呼び出し、継続、トレース
11. プリミティブ         算術・リスト・述語・文字列・ベクタ・I/O・GC・デバッグ
12. 起動                 グローバル初期化、ライブラリ読み込み、REPL、main
```

ファイル上だけ、セクション 9（命令セット）が 8（コンパイラ）より前にある（5日目の決定24。経緯はログ）。
コンパイラが `Op` と `Instruction` を使うので、C++ の宣言順ではそうなる。上の番号は読む順序である。

## 4. アーキテクチャ方針

### 4.1 呼び出し規約（性能設計の中心）

**scheme12 の問題**: 呼び出し1回につき
`Op::ARGS` が引数をリスト化（n個の Pair + n個の Value を確保）→
`vector_from_list` でベクタへ戻す → `make_vector_value` でフレームをベクタ化、
という三重変換をしていた。加えて `vector_from_list` が呼び出しごとに
`std::unordered_set` をヒープ確保していた（除去実験で約18%改善した）。

**scheme13 の方針**:

- **引数はスタック上に積んだまま `APP` に渡す。** `Op::ARGS` を廃止し、
  `APP` / `TAPP` は引数の個数をオペランドに持つ。フレームはスタックの
  該当区間から直接構築する。リストは一切作らない。
- `apply` のときだけリスト化が必要（`Op::ARGS_AP` 相当）。ここは残す。
- **`SEL` のダンプは `c` と `pc` だけを持つ軽量ノードにする。**
  scheme12 は `s` と `e` を丸ごとコピーしていたが、`JOIN` は `c`/`pc` しか
  使っていなかった。
- ~~ダンプは**不変ノードの永続リンクリスト**（scheme12 の設計を踏襲）。
  継続の捕捉が「先頭ポインタを持つだけ」の O(1) になる。~~
  → **4日目に撤回した。**S を連続スタックにすると捕捉はどのみち O(深さ) に
  なるので、この利点は消える。ダンプは連続配列にする。理由は §4.4.2。
- 循環検出は Floyd の2ポインタ法。ホットパスでハッシュ集合を確保しない。

**目標**: scheme12 の 30 万呼び出し/秒に対し、まず 2〜3 倍を目指す。
ベンチは `(define (loop i acc) (if (= i 0) acc (loop (- i 1) (+ acc 1))))` の
100 万回（scheme12 で約 3.4 秒）。

### 4.2 ソース位置

- リーダは各トークンの行・列を記録し、**ソース位置はオブジェクトのヘッダに埋める**
  （3日目の決定12。経緯はログ）。却下した副表（`Pair*` → `SourcePos`）は、キーが強参照になって
  読んだペアが回収されなくなる。位置を持つのはリーダが作ったオブジェクトだけである。
  シンボルと即値の整数は位置を持たない。
- エラー表示の形（**7日目の決定33 で確定**。以後この形を崩さない）:

```
Error: mylib.scm:1:1: car: wrong type of argument
  expected: a pair
  given: 5
    (car 5)
    ^
```

  1行目は `位置: 見出し`。見出しは「**誰が**」「**何をしくじったか**」だけを言う。
  2行目以降は字下げ2の**詳細行**で、`expected:` → `given:` の順。
  最後に問題のソース行とキャレット（字下げ4）。

  **見出しの語彙は次に限る。** 増やすときはこの表に足してから使うこと。

  | 見出し | 使うところ |
  | --- | --- |
  | `<who>: wrong type of argument` | 型が違う |
  | `<who>: wrong number of arguments` | 引数の数が違う（クロージャもプリミティブも） |
  | `<who>: index out of range` | 文字列・ベクタへの添字 |
  | `<who>: argument out of range` | 値そのものの範囲（ASCII コード、長さ、乱数の上限） |
  | `bad syntax in <form>` | 構文検査（セクション6/7/8） |
  | `unbound variable: <name>` | 未束縛の参照 |
  | `attempt to call a non-procedure` | 呼べないものを呼んだ |
  | `internal error: <what>` | **処理系自身の不変条件が壊れた。利用者の誤りではない** |
  | `<who>: cannot run program` | `system` がプロセスを起動できなかった。`given:` はプログラム名 |
  | `exception handler returned` | ハンドラが値を返した。失敗した式の続きは走らない |

  詳細行のラベルは `expected` / `given` / `note` の3つ。`note` は expected/given に
  当てはまらない補足（未束縛の説明、内部エラーの断り書き）にだけ使う。
  綴りは `detail()` / `expected_given()`（セクション2）に閉じ込め、
  各所で文字列を組み立てない。

- **位置の継承は鎖である**（11日目の決定52）。展開が生んだフォームは位置を
  持たないので、`comp` / `comp_body` は `inherited`（囲みフォームの位置）を
  引き継ぐ。**一箇所でも `nearest_pos` を引き直すと、そこから下が丸ごと位置を
  失う。** `lambda` を作る場所を足すときは、`comp` が解決済みの `pos` を
  必ず渡すこと。回帰は `selftest_macro_positions`。

- **`given:` には「悪い部分そのもの」を出す。** フォーム全体はキャレット行が
  見せている。`(let ((a 1) b) a)` で `given: b` と言えれば、読む側は探さずに済む。

- **前置きは2種類。** REPL は `Error:` を付けて次の入力へ進み、`--load` 中は
  `Fatal error:` を付けて終了コード1で止まる。**読み進めるかどうかの違い**を
  前置きで表す。同じ文面を両方で使う。

### 4.3 再帰の禁止事項

scheme12 では C スタックを溢れさせるバグが2件あった。設計として禁じる。

- **リストの cdr 方向を再帰で辿らない。** `equal?`、`to_string`、`length`、
  `append` などは必ずループにする。car 方向のみ再帰してよい。
- 循環検出の `visited` は「経路上のノード集合」として扱い、
  走査後に自分が入れた分を必ず取り除く（バックトラック）。
  そうしないと共有構造（DAG）を循環と誤判定する。

### 4.4 命令セットと機械の状態（4日目に確定）

**先に紙の上で決めたもの。コードより先にここを読むこと。**

#### 4.4.1 scheme12 の実測から分かった、本当のボトルネック

VM を読み直したところ、`ARGS` の三重変換（§4.1）は**いちばん大きい問題では
なかった**。呼び出し1回あたり、scheme12 は次を全部やっている。

| # | scheme12 がやっていること | 計算量 |
| --- | --- | --- |
| 1 | `ARGS` が引数をリスト化（n個の Pair + n個の Value） | O(n) 確保 |
| 2 | `APP` が `vector_from_list` でベクタへ戻す（`unordered_set` をヒープ確保） | O(n) 確保 |
| 3 | フレームを `Vector` 値にする | 2回の確保 |
| 4 | **`d = dump_push(d, DumpFrame{s, e, c, pc})` で `s` と `e` を丸ごとコピー** | **O(環境の深さ)** |
| 5 | **`new_e = [frame] + clo->captured_env` で環境ベクタを毎回作り直す** | **O(環境の深さ)** |
| 6 | `LDG` が大域変数を**名前で毎回ハッシュ検索** | 参照ごとに1回 |

4・5・6 は §4.1 に書かれていなかった。とくに **4 と 5 は環境の深さに比例する
コピーが呼び出しごとに2回**走る。ベンチのループ本体は `loop` `=` `-` `+` の
4つが大域変数なので、6 だけで**1周あたり4回のハッシュ検索**が入っている。

#### 4.4.2 機械の状態

| 記号 | scheme12 | **scheme13** | 効果 |
| --- | --- | --- | --- |
| S 스택 | `ValueVec` を呼び出しごとに退避・クリア | **単一の連続スタック `ValueVec stack`**。呼び出しは `base` 添字を記録するだけ | コピーが消える |
| E 環境 | フレームの `ValueVec`（呼び出しごとに作り直す） | **フレームの連結リスト `Env*`**。1呼び出し = 1確保 | O(深さ) が O(1) に |
| C コード | `Code*` + `pc` | 同じ | — |
| D ダンプ | 不変ノードの永続リンクリスト（`s`/`e` のコピー入り） | **連続配列 `RootVec<DumpEntry>`**。要素は `{c, pc, env, base}` の POD | 確保が消える |

`Env` は Scheme の値ではないので `Object` を継承しない。**可変長の末尾配列**を
持ち、1フレーム = 1回の `GC_MALLOC` で済ませる。

```
struct Env { Env* next; std::uint32_t size; ValuePtr vals[]; };
```

**却下案 A: ダンプを永続リンクリストのまま残す**（§4.1 の当初の決定）。
理由は「継続の捕捉が先頭ポインタを持つだけの O(1) になる」だったが、
**S を連続スタックにした時点でこの利点は消える**。捕捉はスタックの生存区間を
コピーせざるを得ず O(深さ) になるので、ダンプだけ O(1) でも意味がない。
連続配列なら呼び出しごとの確保がゼロになる。§4.1 のこの一文は 4日目に撤回した。

**却下案 B: `if` を SEL/JOIN でなくジャンプ命令にする。** `if` 1回あたりの
ダンプ操作が完全に消えるので速いが、(a) SECD 機械としての性質（D が制御の
退避先である）が薄れる、(b) 逆アセンブル表示が入れ子でなくラベル付きの
平坦な列になり §1.5 の看板機能が読みにくくなる。
連続配列ダンプにした時点で SEL の push は「配列に16バイト積む」だけなので、
残る差は小さいと判断して却下。**性能が足りなければ最初に見直す候補はここ。**

#### 4.4.3 継続

`call/cc` は S とダンプ配列の**スナップショットをコピーして持つ**。
起動時は書き戻す。ダンプの `base` は添字なので、コピーしても整合する。
環境（`Env*`）はコピーせず共有する — `set!` が捕捉をまたいで見えるのは
正しい意味論で、scheme12 も（フレームの実体は共有していたので）同じだった。

捕捉のコストは O(スタックの深さ)。call/cc はホットパスではないので許容する。

#### 4.4.4 大域変数は「セル」で持つ

**`LDG` / `GSET` / `DEF` は名前でなく `GlobalCell*` をオペランドに持つ。**
コンパイル時に `global_cell(name)` でセルを作る（未定義でも作る）。
実行時は 1回のロードと未束縛チェックだけ。ハッシュ検索が消える。

```
struct GlobalCell { ValuePtr value;  // nullptr なら未束縛
                    ValuePtr macro;  // マクロなら変換子、それ以外は nullptr
                    GcString name; };
```

`g_globals` と `g_macros` の2表（scheme12）を**1つのセルに統合**する。
原典がシンボルのプロパティリスト1箇所に両方入れて car で見分けていたのと
同じ構造に戻る（`micro_scheme8_notes.md` §3.3）。前方参照は、未束縛のセルを
先に作っておけば自然に解決する。

#### 4.4.5 命令セット

`Op::ARGS` は**無い**（引数はスタックに積んだまま）。`Op::LDCT` も**無い**（決定7）。

| 命令 | オペランド | 動作 |
| --- | --- | --- |
| `LD` | a=フレーム番号, b=位置 | 局所変数を積む。環境を a 回辿る |
| `LDC` | p1=定数 | 定数を積む |
| `LDG` | p1=`GlobalCell*` | 大域変数を積む。未束縛ならエラー |
| `LDF` | p1=`Template*`, b=使い捨ての印 | 雛形と現在の環境からクロージャを作って積む。**b=1 なら「直後の `APP` に消費されて即座に死ぬ」印**で、VM は確保せずスクラッチを使い回す（12日目の決定54） |
| `APP` | a=引数の個数 | スタック上の `arg0 .. arg_{n-1} callee` を呼ぶ。ダンプを積む |
| `TAPP` | a=引数の個数 | 同上。ダンプを積まない（末尾呼び出し） |
| `ARGS_AP` | a=個数 | `apply` 用。末尾のリストと手前の a-1 個を1つのリストにまとめる |
| `APPLY` / `TAPPLY` | — | `apply` 用。callee と引数リストを取り出して呼ぶ |
| `RTN` | — | ダンプを1つ戻す。空なら実行終了 |
| `SEL` | p1=真の枝, p2=偽の枝 | 分岐。ダンプに戻り先を積む |
| `SELR` | p1=真の枝, p2=偽の枝 | 末尾位置の分岐。ダンプを積まない |
| `JOIN` | — | `SEL` の戻り先へ帰る |
| `POP` | — | 1つ捨てる |
| `DEF` | p1=`GlobalCell*` | 大域定義。**シンボルを残す**（§2.4） |
| `DEFM` | p1=`GlobalCell*` | マクロ定義。セルの `macro` 側に入れる |
| `LSET` | a, b | 局所変数への代入。**代入した値を残す**（§2.4） |
| `GSET` | p1=`GlobalCell*` | 大域変数への代入。同上 |
| `CALLCC` / `TCALLCC` | — | 継続を作って、積んである関数に適用する |
| `STOP` | — | 実行終了 |

**呼び出しの約束**: `APP n` の時点でスタックは下から
`... arg0 arg1 ... arg_{n-1} callee` の順（**callee が一番上**）。

> **5日目に訂正**: ここは当初「callee が先（下）」と書いていたが、
> **scheme12 は引数を左から順に評価してから最後に演算子を評価する**
> （`comp` が `for(args) comp(a); ARGS; comp(head); APP` の順に出す）。
> 評価順はスタックの順序そのものなので、callee を下にすると
> `((begin (display "f") car) (begin (display "a") '(1)))` のような式の
> 出力順が変わる。§1.4 の優先順位1（既存資産とバイト単位で同じ出力）を
> 守るため、**評価順は scheme12 のまま**にし、callee を一番上に置く。
> 引数は `[sp-1-n, sp-1)` の区間にあるので、フレームの切り出しは同じく素直。

`apply` だけは引数の個数がコンパイル時に決まらないので、`ARGS_AP` で
リストにまとめてから `APPLY` / `TAPPLY` で呼ぶ（§4.1 の「apply のときだけ
リスト化が必要」）。`APP` に動的な個数を渡す方式は、callee の評価中に
別の `apply` が走ると個数を保持する場所が壊れるので採らない。

#### 4.4.6 `Instruction` の持ち方（§9 の保留を解消）

**固定長 32 バイトの構造体。**汎用のポインタ枠を2つ持ち、意味は命令ごとに
上の表で決める（型付きのアクセサ関数を1箇所だけ用意し、キャストはそこに閉じる）。

```
struct Instruction {
    Op            op;    // 1
    std::uint16_t a, b;  // フレーム番号 / 位置 / 引数の個数
    SourcePos     pos;   // 実行時エラーに位置を添えるため（§1.4 の優先順位3）
    void*         p1;
    void*         p2;
};
```

却下案: `std::variant` / 命令種別ごとの副表。前者は最大要素に合わせて太り、
後者は逆アセンブルとトレースが2箇所を引き回すことになる。
scheme12 の 100バイト超（`std::string` + `std::vector<std::string>` +
`optional<std::string>` が常に同居）に比べれば固定長32バイトで十分小さい。

`LDF` の `Template` はコンパイル時に1個だけ作る:

```
struct Template { GcVec<GcString> params; std::optional<GcString> rest;
                  Code* body; GcString name; };
```

`LDF` の実行は「雛形と現在の環境を束ねる」だけになり、クロージャ生成のたびに
仮引数名の配列を複製しない（scheme12 は `lambda_params` を毎回コピーしていた）。

### 4.5 `eval` と環境（2026-10-01 に設計し、同日実装）

R5RS 6.5 の4手続きを足す。`eval`、`interaction-environment`、`scheme-report-environment`、`null-environment`。いずれも**手続き**である。`call/cc` のような特殊形式にはしない。`(procedure? eval)` は `TRUE`。

**フレーム（`Env*`）は値にしない。** 環境指定子は大域の表を指す別の値で、3つだけ存在する。同じ手続きを2回呼んだ結果は `eq?` で真。表示は `#<environment:interaction>`、`#<environment:scheme-report>`、`#<environment:null>`。読み戻せない。§2.1 と `spec_test.scm` の末尾（2.1-29 から）がこの3行である。

| 手続き | 引数 | 中身 |
| --- | --- | --- |
| `interaction-environment` | 0個 | REPL が使っている大域の表そのもの |
| `scheme-report-environment` | 整数 `5` だけ | 起動時ライブラリを読み終わった直後の表の写し |
| `null-environment` | 整数 `5` だけ | 組み込み特殊形式の写しと `:undef`。`+` も利用者マクロも無い |

`5` 以外の整数は `argument out of range`。整数でないものは `wrong type of argument`（`expected: an integer`）。引数の個数が違うときは `wrong number of arguments`。

報告書の環境は、起動時ライブラリを読み終わった直後に、値かマクロが入っているセルを**別のセルへ写す**。手続きオブジェクトは共有してよい。セルは共有しない。利用者があとから `define` や `set!` しても、写しの側は動かない。写しは1回だけで、最初に呼ばれたときへ遅らせない。写したあとで、`scheme-report-environment` 自身を対話環境と報告書の両方へ入れる。それより前の名前は未束縛で、今と同じ `unbound variable` になる。空の環境の特殊形式は、この写しの時点で特殊形式オブジェクトが入っているセルだけを別セルへ写す。それに加えて `:undef` も写す。`letrec` と `cond` の展開がこの大域を読むので、写さないと内部 `define` が `unbound variable: :undef` になる。`+` は写さない。

`eval` は呼び出し元の局所変数を見ない。`(let ((x 1)) (eval 'x (interaction-environment)))` の `x` は、その `let` ではなく大域である。コンパイル環境が空なのはこのためである。局所で隠したつもりでも、特殊形式の判定は今どおり名前が先である。`(let ((if list)) (if 1))` は `if` 式のままである。eval のためにこの順序は変えない。

**組み込みの特殊形式は、どの環境でもコンパイラが名前で判定する。** 今と同じく、利用者マクロより先である。`let` という名前のマクロでは覆せない。

**定義と大域への代入は、対話環境だけが受け付ける。** `define`、`define-macro`、大域の `set!` をほかの環境でコンパイルしたら `bad syntax in <form>` とし、`note` は `accepted only in the interaction environment` と書く。見出しの語彙は §4.2 のまま足さない。`lambda` 本体の内部 `define` と、局所変数への `set!` は環境を書き換えないので、どの環境でも今どおり動く。

**未束縛の参照は、実行がそこへ到達したときに今と同じ `unbound variable` で止まる。** 到達しなければ止まらない（`(if #f 無い名前 1)` は `1`）。対話環境では、今どおり参照の時点でセルを表へ作る。前方参照がこれで埋まる。ほかの環境では、名前付きのセルを LDG のオペランドにはするが、**表には入れない**。

利用者マクロを展開するとき見る表は、その評価の環境だけである。組み込みの `let` や `cond` の展開は表を見ない。

**式は、`eval` を呼んだのと同じ VM で実行する。** 別の VM を立てない。`compile_top` は使わない。あれは `STOP` で終わり、`STOP` は VM の `run()` ごと戻るので、呼び出し元が消える。コンパイルは空のコンパイル環境で行い、本体は `RTN` で終わる。

入るときのスタックはクロージャ呼び出しに揃える。末尾でなければ、ダンプに戻り先を積み、スタックを引数の位置まで縮め、`base` をそこへ移し、`env` を空にしてから跳ぶ。末尾ならダンプは積まず、スタックは今の `base` まで縮める。`RTN` は `base` まで捨てて結果を1つ残すので、ここがずれると呼び出し元のスタックが壊れる。通常のプリミティブのように値を返してから跳んではならない。跳ぶ前にコンパイルが失敗したときは、まだ跳んでいないので、そのエラーがそのまま出る。対話環境に、失敗するまでに作った未束縛セルが残ることがある。ロードや REPL も今そうなので、eval だけでは片付けない。

したがって式の中の `call/cc` は、`eval` の呼び出し元まで含んで捕捉する。`(call/cc (lambda (k) (eval (list k 9) (interaction-environment))))` は `9`。`'(k 9)` はシンボル `k` を対話環境で引くので、その `lambda` の継続にはならない。式のデータに継続そのものが混ざるのは、リーダが作らない原子を定数（`LDC`）として積むからである。式の中で捕まえた継続を、`eval` が戻ったあとから起動すると、その式の続きへ戻り、結果は `eval` の呼び出し元へ届く。`dynamic-wind` の入れ子も、今の1本のまま見る。`(eval '(exit 0) ...)` は、今の `exit` と同じくプロセスを終える。

別 VM のまま残すものは2つある。マクロ変換子と `load` である。変換子の中の `set!` は、そのマクロを定義したときに焼き込まれたセルを書く。報告書の環境で展開しても、変換子をコンパイルし直さない。`load` が読む各フォームは、今どおりロード側の実行である。どちらも eval の式そのものの規則ではない。

却下した案は次である。

- フレーム `Env*` を Scheme の値にして、レキシカル環境を `eval` に渡す。呼び出し規約の中心が動く。R5RS の第2引数は、上の3つのどれかである。
- `eval_top` のように新しい VM で式を `run()` する。マクロ変換子はこの道で正しい。利用者の式で使うと、継続が内側の VM だけを捕まえる。13日目に避けた穴である。
- 報告書の環境を、R5RS の名前一覧でもう1枚メンテナンスする。この処理系の初期束縛（`error` や `load` を含む）とずれる。
- 命令を1つ足す。どの表を見たかは、コンパイル時にセルへ焼き込む。実行ループは表を知らない。熱い道の命令列は変わらない。

`eval` の第2引数が環境指定子でなければ `eval: wrong type of argument`、`expected: an environment`。式の中で起きたエラーの見出しは、その式を直に評価したときと同じにする。`eval:` では包まない。位置を持つ式はそこを指す。`cons` で組んだ式は位置を持たないので、VM が `eval` の呼び出し位置を貼る（今の規則のまま）。

`--selftest` にあるもの。互換ゴールデンは1バイトも変えていない。`spec_test.scm` には §2.1 の3行を足してある。

- `(eval '(+ 1 2) (interaction-environment))` と報告書の環境は `3`。空の環境は `unbound variable: +`。
- `(eval '((lambda (x) x) 7) (null-environment 5))` は `7`。局所の `set!` も空の環境で動く。`(eval 'if (null-environment 5))` は特殊形式で、`(eval '+ (null-environment 5))` は未束縛。
- `(let ((x 1)) (eval 'x (interaction-environment)))` は大域の `x` を見る。`let` の `1` は見えない。
- 対話環境で `(eval '(define (f) later) ...)` のあと `(eval '(define later 8) ...)` し、`(eval '(f) ...)` は `8`。
- 対話環境での `(eval '(begin (define zz 4) zz) ...)` は `4` で、その後の `zz` も `4`。同じ定義は報告書と空では `bad syntax`。
- 対話環境で定義した名前は、報告書の環境からは見えない。対話環境で `set!` した初期手続きは、報告書の側では初期のまま。
- 対話環境の利用者マクロは、その環境の `eval` では展開される。空の環境では展開されない。
- `(call/cc (lambda (k) (eval (list k 9) (interaction-environment))))` は `9`。ここが落ちる実装は、別 VM で走らせている。`'(k 9)` は大域の `k` を見る。
- 3つの環境は互いに `eq?` で偽。同じ手続きの2回の結果は真。
- 引数個数、版の `5` 以外、環境でない第2引数は、上の見出しで落ちる。

### 4.6 `system`（2026-10-02 に設計し、同日実装）

原典 `micro_Scheme8.lisp` の外部コマンド実行を、手続き `system` として入れた。解説は [scheme14解説.md](scheme14解説.md)。Windows での実コマンド確認は `tests/system_win_test.scm`。Linux（WSL2）での確認は解説の §2.7 で、2026-10-03 に通った。

`(system program arg ...)`。`program` と各 `arg` は文字列で、1個目は必須、2個目以降は何個でもよい。`(system "git" "status")` も `(system "git")` もこの形である。引数はデータであり、シェルのスクリプトではない。`&&` や `|` や引用符を、この手続きは解釈しない。

戻り値は終了コードの整数である。`0` が成功。POSIX でシグナル終了したときは `128` にシグナル番号を足す。Windows の終了コードは 255 で切らない。起動できなかったときは終了コードを返さず、`system: cannot run program` とし、`given:` にプログラム名を書く。引数が0個なら `wrong number of arguments`。文字列でない引数は `wrong type of argument`、`expected: a string`。

子プロセスには、scheme14 自身が OS から受け取った標準入力・標準出力・標準エラーを継がせる。`current-output-port` や `with-output-to-file` の先には流さない。子が終わるまで `system` は戻らない。

OS の名前は、この手続きの本体にだけ書く。Scheme から OS を尋ねる手続きは足さない。できた実行ファイルには、ビルドした側の起動処理だけが残る。

- Linux と Unix は `posix_spawnp` で PATH を探し、`waitpid` で待つ。`fork` は使わない。Boehm GC のロックを子が抱えないためである。
- Windows は `CreateProcess` で起動し、終了を待つ。プログラム名は `open-input-file` と同じバイト列で渡し、この処理系の中でワイド文字列へ変換しない。引数の列は、Windows がコマンドラインを分解する規則で、この手続きが引用符を付けてから渡す。利用者が OS ごとに引用符を書くことはない。ディレクトリ区切りの無い名前は PATH から探し、拡張子が無ければ `.exe` を補う。

新しいライブラリは足さない（§1.2）。`posix_spawnp` は libc、`CreateProcess` は Windows のビルドが既にリンクしている範囲である。

却下した案は次である。

- 標準 C の `system` にコマンドライン文字列を1つ渡す。ソースに OS の名前は要らないが、Windows のビルドでは `cmd.exe`、Unix のビルドでは `sh` がその文字列を読む。
- 原典の引数の形 `(system prog arg1 (list ...))` を保つ。`run-program` がリストを要求していた写しなので、残りの引数を並べる形にする。
- `fork` してから `exec` する。
- 子の出力を `current-output-port` へ繋ぐ。

### 4.7 `number->string` と `string->number` の基数（2026-10-03 に設計し、同日実装）

R5RS が許す第2引数のうち、**正確な整数を 2、8、16 で読み書きする分だけ**を足した。引数1個の呼び出しと、基数 10 は、今の10進の経路のままである。使い方は [scheme14解説.md](scheme14解説.md) の第3章。

第2引数は正確な整数で、値は 2、8、10、16 のいずれかである。省略したときは 10 とみなす。個数は `need_args` で 1 から 2 にする。0 個や 3 個以上は `wrong number of arguments`、`expected: 1 to 2 arguments`。

基数の検査は、第1引数が手続きの求める型だと分かったあとで行う。

- 正確な整数でない基数（`16.0` や文字列）は `wrong type of argument`、`expected: an integer`。実数を整数の場所で受けないのは決定92のままである。`num_of` を使う。
- 正確な整数だが 2、8、10、16 のどれでもないときは `argument out of range`、`expected: 2, 8, 10, or 16`。

**引数が1個のとき、および基数が 10 のとき。** `number->string` は `to_string`（決定90。`write` と同じ表示）、`string->number` は `parse_number`（決定89。リーダと同じ文法）を呼ぶ。実数、`+inf.0`、`+nan.0` も今どおりである。この2つの関数に基数の引数は足さない。10進の書式を2つ持たない。

**基数が 2、8、16 のとき。** 対象は正確な整数だけである。

- `number->string` の第1引数が正確な整数でなければ `wrong type of argument`、`expected: an exact integer`。`8.0` や `1.5` や `+inf.0` はここである。数でないものは、基数を見る前に `expected: a number` で止まる。
- 出力に `#x` や `#b` の接頭辞は付けない。16進の `a` から `f` は小文字にする。負なら先頭に `-` を付ける。正に `+` は付けない。余分な先頭の 0 は付けない。0 は `"0"` である。桁数の上限は置かない。`BigInt` のまま、割った余りで桁を作る。
- `string->number` は、文字列全体が「符号が任意で1つ、その後にその基数の数字が1つ以上」のときだけ正確な整数を返す。2進は `0` と `1`、8進は `0` から `7`、16進は `0` から `9` と `a` から `f` と `A` から `F`。入力の大文字と小文字は同じ数字である。先頭の 0 は許す。`"+10"` も `"-0"` も受け、`-0` の値は正確な 0 である。空白、小数点、指数、`#` で始まる接頭辞は受けない。形が外れたらエラーにせず `false` を返す。`1.5` を16進で渡したときも `false` である。変換は桁を基数倍して足す。

往復は、正確な整数 `n` と基数 `r`（2、8、10、16）について `(string->number (number->string n r) r)` が `n` と `eqv?` で真になることである。

リーダは変えない。`#b` `#o` `#d` `#x` `#e` `#i` は数の接頭辞にしない。決定89の「数の文法は一つ」は10進の `parse_number` の話として残す。2、8、16 の変換は、その基数が渡されたときのこの2手続きの中だけに置く。

却下した案は次である。

- 2、8、16 で不正確な数も出す。倍精度を読み戻す書式は、10進の `to_chars` とは別の仕事になる。
- リーダに `#xff` や `#b101` を足す。凍結してあるトークンの規則（§2.5）が動く。
- 2、8、10、16 以外の基数も受ける。R5RS が定める四つに限る。
- 出力を大文字にする、または `#x` を付ける。往復の文字列を一つに決められない。

実装するときは `--selftest` に、上の往復、大文字の入力、形が外れたときの `false`、基数と型のエラーを足す。ゴールデンには入れない。§2 の凍結した表示は変えない。

### 4.8 準クオートのネスト（2026-10-04 に設計し、同日実装）

R5RS 4.2.6 のネストは、`qq_transfer` の深さで入っている。リーダ、命令、コンパイラの他の特殊形式は変えていない。バッククオート、カンマ、カンマアットは `quasiquote`、`unquote`、`splice` として読まれる。

**深さはテンプレートを1段入るたびに数える。** 外側の `quasiquote` を剥がした直後が深さ 1 である。`expand_form_1` が渡す。`quasiquote` を見たら 1 増やし、`unquote` と `splice` を見たら 1 減らす。深さが 1 の `unquote` と `splice` だけが「ここで評価する」である。それより深いものは、評価せずに同じシンボルのリストとして結果に残す。

リストの car がシンボル `quasiquote`、`unquote`、`splice` のいずれかなら、そのリストはその構文である。要素として現れたときも、cdr を辿った残りがそのリストそのものであるときも、同じ規則で見る。`(a . ,v)` と `(a unquote v)` は同じリストなので、今どおり後者もドット位置の unquote である。

構文として見たリストは、引数がちょうど 1 個の適正なリストである。0 個、2 個以上、ドットで終わっているものは `bad syntax in quasiquote`。`expected:` は `(quasiquote expression)`、`(unquote expression)`、`(splice expression)` のどれかで、`given:` はそのリストである。実装前の深さ 1 は `(unquote a b)` の余分な引数を捨てて `a` だけを採っていた。この抜けは、同じ検査で閉じた。

展開は今の `cons` と `append` と `(quote ...)` のままである。空リストは `(quote NIL)`。数も文字列も quote する。`(quote a)` と `(quote b)` を `(quote (a b))` に畳まない。畳むと、ネストを含まない既存の展開文字列が変わる。

- **ベクタ**は、要素を同じ深さでリストとして展開し、`list->vector` で戻す。
- **上の 3 シンボル以外のアトム**は `(quote それ)`。
- **`quasiquote`** は、中のテンプレートを深さ +1 で展開し、`(cons (quote quasiquote) (cons その展開 (quote NIL)))` で包む。
- **`unquote`** は、深さ 1 なら式をそのまま置く。その式の中へは降りない。深さ 2 以上なら、式を深さ −1 で展開し、`unquote` を同じ cons の形で包む。
- **`splice`** は、深さ 1 なら式をそのまま置き、今どおり `append` の引数にする。深さ 2 以上では `append` にしない。`splice` を包んだものを、普通の要素として `cons` する。
- **それ以外のペア**は、car を同じ深さで展開して `cons` し、cdr は今どおりループで辿る。cdr 方向には再帰しない（§4.3）。深さを下げる再帰は、バッククオートの入れ子とリストの car だけに乗る。

深さ 1 で、`splice` がリストの要素でもベクタの要素でもない位置にあるときは、引数が 1 個でも今のエラーのまま止める。`note` の文は変えない。`unquote-splicing (,@) is not allowed in the tail position of a dotted list`。トップレベルの `,@x` もこの位置である。深さ 2 以上の同じ位置はエラーにしない。`` `(a `(b . ,@x)) `` は、内側をデータ `(b splice x)` として残す。

`quote` はカンマを止めない。R5RS の `` ,',name `` は、引用の中のカンマも深さだけで決まる。有効な `unquote` の式はテンプレートではないので、その中のカンマはここでは見ない。`` `,,x `` は式 `(unquote x)` をそのまま置く。展開時にはエラーにしない。式の中に別の `quasiquote` があるとき、たとえば `` `(,(list `(b ,y))) `` の内側は、`list` の引数としてコンパイラが後から普通の準クオート（深さ 1）として展開する。ここで先に展開すると、二度展開するか、データとして残すべきバッククオートまで消える。

リーダは変えない。手書きの `(unquote-splicing x)` は `splice` と認めない。`unquote-splicing` を別名で足さない。結果の表示も略記に戻さない。`(quasiquote (b (unquote foo)))` のまま書く。§2.1 の表示は変えない。

ネストを含まないテンプレートの展開文字列は、今の `--selftest` の 4 件と一致したままにする。`` `(a ,x) ``、`` `(,k . ,v) ``、`` `(a ,@b c) ``、`` `#(1 ,x) ``。

`--selftest` にあるのは次である。ゴールデンの既存 12 件には、バッククオートのネストは無い。`spec_test.scm` の §2.5 は採り直してある。

- `` `(a `(b ,x)) `` の値は `(a (quasiquote (b (unquote x))))` である。内側のカンマが 1 つのときは、変数 `x` を評価しない。シンボル `x` がデータのまま残る。
- `` `(a `(b ,,x)) `` の展開は `(cons (quote a) (cons (cons (quote quasiquote) (cons (cons (quote b) (cons (cons (quote unquote) (cons x (quote NIL))) (quote NIL))) (quote NIL))) (quote NIL)))`。こちらは `x` を評価する。
- `` `(a `(b ,@,xs)) `` の内側は `append` ではない。`(cons (quote splice) (cons xs (quote NIL)))` を `cons` する。
- `(let ((name1 'x) (name2 'y)) `(a `(b ,,name1 ,',name2 d) e))` の値は `(a (quasiquote (b (unquote x) (unquote (quote y)) d)) e)`。
- `(let ((x 'foo)) ``,,x)` の値は `(quasiquote (unquote foo))`。カンマが 1 つ多い `` `,,x `` は展開でき、値は実行時に `unquote` を評価した結果である。
- `` `(a . ,@v) `` は今の `note` のまま。`(quasiquote (unquote a b))` は `expected: (unquote expression)`。

§2.5 の該当行は次である。`spec_test.scm` は 2.5-04 にこの行があり、実数のリテラル以降は 2.5-09 まで繰り下がっている。ファイル先頭の「無い、という主張」にネストの句は無い。`syntax-rules` の句は残してある。

- 準クオートはネストする。カンマは同じ深さのバッククオートだけを打ち消す。`(let ((x 'foo)) `(a `(b ,,x)))` は `(a (quasiquote (b (unquote foo))))`。表示は略記にしない。

`scheme13解説.md` の本文は動かさない。あちらの「ネストは未対応」は scheme13 の説明である。scheme14 の説明は `scheme14解説.md` に書く。

却下した案は次である。

- 内側の準クオートも展開しきって、残りのカンマをデータとして後から組み立てる。深さの帳尻を二箇所で持つことになる。
- 有効な `unquote` の式の中まで歩く。`` `,,x `` の余ったカンマまで外側が食べる。
- 隣り合う `(quote a)` と `(quote b)` を `(quote (a b))` に畳む。深さ 1 の展開が変わる。
- `unquote-splicing` も `splice` と同じに認める。リーダが作る名前は `splice` だけである。
- 循環リストの準クオートを検出する。今も検出していない。この節では足さない。
