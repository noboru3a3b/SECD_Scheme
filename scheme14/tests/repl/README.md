# REPL を人が触る筋道（27日目）

**ここにあるのは REPL の入力そのものである。** `run_golden.sh` の
「REPL の筋道」の節が `.in` を標準入力に流し込み、**標準出力・標準エラー・
終了状態の3つを別々に**ゴールデンと突き合わせる。

## なぜ要るのか

§9 が15日目から抱えている問い —「テストが開発側の想定した使い方しか
通っていないのではないか」— の残り半分である。26日目に**表示の側については
当たっていた**と測って分かった（決定133）が、**人が REPL を触る筋道は
どのテストも通っていなかった**。`--selftest` も `run_golden.sh` も
`sicp/run_sicp.sh` も、**式を評価させること**しか見ていない。

15日目に `(exit)` が無いことへ14日間気づかなかったのも、根はここである
（決定64〜70）。あのときは終了コード5件だけをシェル側で見るようにして、
残りは未決のまま §9 に積んであった。

プロンプトは **tty かどうかを見ずに必ず出る**ので、パイプで流し込んでも
出力は決定的になる。これは実装の性質に寄りかかった測り方なので、
**プロンプトを tty のときだけ出すように変えたら、ここは全部採り直しになる。**

## 各ファイルが押さえているもの

| ファイル | 主張 |
| --- | --- |
| `basic.in` | 起動の挨拶、`scheme13> ` プロンプト、値が返ること、Ctrl-D（EOF）で `Bye!` と出て終了状態 0 |
| `error_survives.in` | **エラーを打っても REPL が死なない。** 文面は stderr、続きの式はちゃんと評価される |
| `multiline.in` | 括弧が閉じるまで `...>` で読み続けること。**空行は何も起こさず読み直す**だけ |
| `exit_code.in` | REPL から `(exit 3)` で終了状態 3。`Bye!` は**出ない**（EOF ではないので） |
| `help.in` | `(help)` の出力全体。**デバッグ機能は一級市民**（§1.5）なので、文面が動いたらここで気づく |

`(globals)` は**入れていない**。大域名が増えるたびにゴールデンが動くうえ、
名前の集合は決定40 のやり方で機械的に数えるほうが確かだからである。
