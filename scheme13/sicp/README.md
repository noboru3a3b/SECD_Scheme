# SICP を教材にした scheme13 の実地確認

MIT の教科書 *Structure and Interpretation of Computer Programs*
（[全文](https://mitp-content-server.mit.edu/books/content/sectbyfn/books_pres_0/6515/sicp.zip/full-text/book/book-Z-H-4.html)）
を1章ずつ読み、その章の題材を scheme13 で書いて動かす。**目的は SICP を解くこと
ではなく、「教科書の Scheme が、書き写したまま動く処理系か」を実地に確かめること。**

```sh
scheme13/sicp/run_sicp.sh                 # 全章
scheme13/sicp/run_sicp.sh ./scheme13/scheme13 scheme13/sicp/ch1   # 章を指定
```

各 `.scm` は自分で主張を数え、最後に `=== SICP 1.1  total: 46  NG: 0 ===`
の形で締める。ランナーはこの行と終了状態だけを見る。

## 書き方の決まり

1. **書籍の文章やコードを写さない。** 節の主題を自分で書く。
2. **期待値には、書籍が本文に印字している数をそのまま使う。**
   `(my-sqrt 9)` → `3.00009155413138`、`(integral cube 0 1 0.001)` →
   `0.249999875000001` のように、倍精度の最終桁まで書く。**ここが実数の実装と
   印字（最短往復表現）に対する最も厳しいテストになっている。**
3. 桁まで合わせられない場合だけ `check~`（許容誤差つき）を使い、
   **なぜ合わないかをコメントに書く。**
4. ファイルは自己完結させる。`check` / `summary` は各ファイルに同じものを置く。

## 第1章で分かったこと

- **書籍の平方根（1.1.7）・数値積分と π 級数（1.3.1）・区間二分法と不動点

  値が書籍の印字と最終桁まで一致する。** 18〜22日目に入れた倍精度実数は、
  教科書が前提にしている数の振る舞いを満たしている。

- **唯一ずれるのは `(fixed-point cos 1.0)` の最終1桁**
  （書籍 `0.7390822985224023` / この環境 `0.7390822985224024`）。
  同じ反復を C で書いて glibc の `cos` を直に呼んでも `…24` になるので、

- **`(/ 1 3)` が `0` である仕様（決定82）に、第1章は一度も足を取られない。**

  `1.0` を書く必要がある」と見込んだが、**実際には書籍がすでにそう書いている。**

- 22日目以前は、この3ファイルが「整数に読み替えた版」だった

## 第2章で分かったこと

### 見つかった不具合（3件とも 23日目に直した）

1. **`quotient` と `remainder` が、実数を渡されると黙って実数除算になる。**

   ```
   (quotient 7.0 2)   => 3.5      ; 商ではない
   (remainder 7 2.0)  => 0.0      ; 剰余ではない（7 rem 2 は 1）
   (quotient 1 0)     => Fatal error: /: division by zero    ; 見出しが `/`
   (modulo 7.0 2)     => Fatal error: modulo: wrong type of argument  ; こちらは正しい
   ```

   原因は `lib13.scm` の `(define quotient (lambda (x y) (/ x y)))`。
   **整数しか無かった頃は正しかった定義**が、19〜22日目に `/` が実数を受ける
   ようになったことで意味を変えた。

   → **直した**（決定118）。C++ のプリミティブへ移し、`modulo` と同じ文面で
   実数を弾く。0除算の見出しも自分の名前になった。**別名をやめること自体が
   修正**で、`/` の別名である限り次に `/` の仕様が動けば同じことが起きる。

2. **4段の `c…r` が無かった。** `caar` から `cdddr` までの12個（2段と3段）は
   あったが、R5RS が定める4段の16個（`cadddr` / `cddddr` など）が無かった。
   2.3.4 のハフマン符号木で踏んだ。

   → **直した**（決定119）。`lib13.scm` に16個。テスト側の補いは外した。

3. **`map` が「手続き＋リスト1本」しか取らなかった**（R5RS は複数を許す）。
   演習 2.36〜2.37（`accumulate-n`・行列積）で踏んだ。

   → **直した**（決定119）。`set!` で拡張し、**1本のときは `system_lib.scm` の
   実装をそのまま呼ぶ**ので既存資産は動かない。`for-each` の複数リストは
   まだ無い。

**3件とも「開発側が書かない書き方」で踏んでいる**（`quotient` に実数を渡す・
`cadddr` を使う・`map` に2本渡す）。`selftest` もゴールデンも開発側が思いつく
使い方しか通らないので、**外から来た題材にしか見つけられない穴がある。**

### 仕様どおりに動いていて、教科書と食い違う点

- **`(/ 1 3)` が `0`**（決定82）。第2章では演習 2.38（`(fold-right / 1 (list 1 2 3))`）
  で表に出る。書籍は有理数で `3/2` になるが、整数で書くと途中で `(/ 2 3)` が `0` に
  なり、**次の割り算が0除算になって落ちる。** 実数で書けば書籍と同じ 1.5 になる。
- **有理数型・複素数型が無い**（§2.3）。ただし第2章は**その2つを対とタグで自分で
  作る章**なので、むしろ題材とかみ合っている。2.5 の型の塔も Scheme 側で組める。
- **`sqrt` は正確さを保つ**。`(magnitude (3 . 4))` は `5`（正確）、
  `(magnitude (3.0 . 4.0))` は `5.0`。テストの期待値もそう書き分ける必要がある。
- **Scheme レベルの例外捕捉が無い**（§1.4-3）。「エラーになること」を主張する
  テストがファイル内に書けないので、`*_error.scm` を別に置き、
  終了状態と文面をランナーが見る形にした。


## 第3章で分かったこと

**処理系の不具合は1件も出なかった。** 落ちた3件はすべてテスト側の誤りで、
内訳は「2の冪を法とする線形合同法の下位ビットを使ってしまった」
「`set-car!` の返り値を勝手に `:undef` と決めつけた」
「オイラー変換の収束の速さを1桁見誤った」である。

### この章がとくに効いた点

- **`delay` / `force` が値を覚える。** 3.5 が要求する memo-proc が
  `system_lib.scm` にすでに入っている。覚えないと無限ストリームの計算量が
  膨らみ、篩による素数列（`(stream-ref primes 50)` → `233`）や
  π の加速（8項で倍精度の限界まで）が現実的な時間で終わらない。
  **`(stream-ref fibs 100)` が bignum になっても列は壊れない。**
- **`define-macro` で `cons-stream` が書ける。** 第2引数を評価しない特殊形式が
  利用者の側で作れることが、この章の前提になっている。
- **3.3.4 の論理回路（議事日程つき）と 3.3.5 の制約の伝播が、
  一度も直さずに通った。** 第3章で最も大きい2つのプログラムで、
  局所状態を持つ物を大量に作って繋ぎ、手続きを表に溜めて後で呼ぶ。
  制約網は**向きを持たない**ので、`C` を決めれば `F` が、`F` を決めれば `C` が
  出る（25℃ → 77°F、212°F → 100℃）。
- **環（循環リスト）を作っても処理系は壊れない。** ただし `write` /
  `display` / `equal?` に渡すと止まらないので、テストは `eq?` と
  辿る回数だけで書いてある。

### 仕様どおりだが R5RS/R7RS と違う点

- **`set-car!` / `set-cdr!` は格納した値を返す**（R5RS では未規定）。
  原典から継いだ形で、書籍のコードは返り値を使わないので影響しない。
- **`make-promise` は R7RS のものではない。** `system_lib.scm` のそれは
  `delay` 用の内部ヘルパで、**値ではなく thunk を取る**。
  `(force (make-promise 5))` はエラーになる。`delay` / `force` は正しく動く。
  R5RS に `make-promise` は無いので `lib13.scm` の基準（決定42）の外。

### 3.4（並行性）を対象外にした理由

scheme13 に並行機構が無い（スレッドも `parallel-execute` も無い）。
3.4 の主題は「複数のプロセスが同じ状態を共有するときに何が壊れるか」で、
逐次実行しか無い処理系では**題材そのものが再現できない**。
直列化器（serializer）を1つの実行の中で模しても、
確かめられるのは自分で書いた模型の性質だけで、処理系については何も言えない。


## 第4章で分かったこと

Scheme で書いた Scheme を scheme13 の上で動かし、その中でさらにプログラムを走らせる。
**4種類の評価器（超循環・遅延・非決定性・論理）がすべて動いた。**
処理系側の不具合は出ず、落ちた4件はすべてテスト側の誤りだった。

### この章がとくに効いた点

- **被解釈言語のループ1万回が通る。** 超循環評価器では、被解釈言語の末尾呼び出しが
  `my-eval` → `my-apply` → `eval-sequence` → `my-eval` という**相互再帰**を通って
  scheme13 の末尾呼び出しに落ちる。ここが切れていればスタックが尽きる。
  4.1.7 の解析する評価器でも同じく通る。
- **`amb` 評価器（成功継続・失敗継続）が動く。** 探索の深さがそのまま閉包の
  入れ子の深さになる形で、5人5階のパズルも 20以下のピタゴラス数も出る。
  **後戻りのときに `set!` を取り消す**仕掛けも効いている。
- **遅延評価器の thunk の記憶化**は `set-car!` / `set-cdr!` でその場で書き換える。
  `(try 0 (/ 1 0))` が 0除算を踏まずに `1` を返し、
  無限リスト（`(list-ref integers 17)` → `18`）が特殊形式なしで書ける。
- **質問システム**（照合・単一化・規則の変数付け替え・`and`/`or`/`not`/`lisp-value`）が
  一通り動く。再帰する規則（先祖）も、有限で循環しないデータなら答えが出る。
- **第1〜3章で確かめたものが、ここでまとめて使われる。** 記号データと表（第2章）、
  局所状態と `set!` と変更可能データ（第3章）、閉包と高階手続き（第1章）。
  第4章は単独の機能ではなく、**組み合わせの試験**になっている。

### 書くときに気をつけた点（処理系の性質から来るもの）

- **`apply` は scheme13 では特殊形式**なので、評価器の側の手続きを `apply` と
  名づけて上書きすると足元が崩れる。`my-apply` にした（書籍も別の理由で
  `apply-in-underlying-scheme` を置いている）。`eval` は大域名に無いので空いている。
- **文字は長さ1の文字列**（凍結仕様 §2.2）なので、`?x` を `(? x)` に直す処理は
  `char=?` ではなく `string=?` で書く。
- 4.4 の答えの集合は、書籍がストリームで扱うところを**リストにした**。
  データベースが有限で規則も無限に潜らない形なので結果は同じ。ストリームが
  要るのは無限の答えを扱うときで、それは 3.5 で確かめてある。


## 第5章で分かったこと

レジスタ機械を Scheme の上に作り、その上で**評価器と翻訳系**を走らせる。
**第5章は scheme13 の設計そのものと正面から重なる唯一の章**で、
scheme13 が式を命令列にコンパイルして SECD 機械で走らせるのと、
5.4／5.5 が「評価を明示的な制御の列に落とす」のは同じ主題である。

**処理系側の不具合は1件も出なかった。** 落ちた8件はすべてテスト側の誤りで、
内訳は「命令数の数え違い」5件、「`(const 'zero)` と書いてしまい定数が
`(quote zero)` になった」1件、「対の個数の数え違い」1件、
「まだ定義していない被解釈手続きを呼んだ」1件である。

### この章がとくに効いた点

- **シミュレータの実行ループが末尾呼び出しであること。** 1命令ごとの再帰なので、
  5.4 の評価器で 10000 回のループを回すと**百万命令を超える**。ここが切れて
  いれば何も走らない。実測で通った。
- **`apply` に、実行時に決まる手続きと任意長の引数リストを渡せること。**
  `make-operation-exp` がこれで書かれている（scheme13 の `apply` は特殊形式だが、
  値としての手続きを受ける）。5.5 の `append-instruction-seqs` は
  可変個引数の手続きを `apply` で再帰的に呼ぶ。
- **`set-cdr!` で命令に実行手続きを後から差し込む**アセンブラが動く。
- **被解釈言語の末尾呼び出しが定数の場所で回る。** 5.4.2 の主張を実測した。
  末尾再帰版と、最後の式を特別扱いしない版（演習5.28）を**制御器の
  ev-sequence だけ差し替えて**並べてあり、後者は深さが回数に比例して伸びる。
  5.5 では同じ性質を、生成された命令列の側で測っている。
- **準引用と、命令列をデータとして継ぎ足す書き方**が要る（5.5）。翻訳系は
  「命令の並びを返す手続きの集まり」であって、その値がそのまま
  シミュレータのアセンブラを通る。**生成した符号が 5.1.5 の書式に
  収まっていなければ、そこでアセンブルに失敗する。**
- **ベクタ（`make-vector` / `vector-ref` / `vector-set!`）で記憶を模し、
  停止＆複写のごみ集めをレジスタ機械として走らせられる**（5.3）。
  環（循環リスト）も共有も壊さずに写る。

### scheme13 の設計との対応（5.4・5.5）

| SICP 第5章 | scheme13 |
| --- | --- |
| `continue` レジスタ | 継続に積む戻り番地 |
| `env` レジスタ（枠の連結リスト） | `Env*` の鎖（可変長の末尾配列で1枠1確保） |
| `argl` | 引数フレーム |
| linkage `return` + target `val` | `TAPP`（末尾呼び出し） |
| linkage が label / next | `APP` |
| `preserving` が入れる save/restore | 継続に積む枠 |
| 5.5.6 の字句アドレス `(枠 . 位置)` | `LD (depth index)` |
| 翻訳時に枠が分からない名前 | `LDG` |

**scheme13 は 5.5.6 を既定で行っている。** 局所変数は名前ではなく
「何段外の何番目」で引かれ、`LDG` だけが大域名のために残っている。
5.5.6 を通すことは、その設計が教科書の言うとおりのものであることの確認になる。

### 書くときに気をつけた点（処理系の性質から来るもの）

- **翻訳された符号を走らせる機械は1つでなければならない。** 翻訳された
  手続きの値は「入口のラベル」＝*その機械の*命令列の中の一点を指すので、
  式ごとに機械を作り直すと、前に定義した手続きの入口が別の機械のレジスタを
  掴んだままになり、呼び出した先で `proc` が空になる。5.5.7 が翻訳した符号を
  評価器の機械へ「積み込む」形にしているのは、まさにこの理由である。
- **制御器の中の `(const 'zero)` は定数 `(quote zero)` になる。** 制御器の
  文そのものが引用されたリストなので、その中でさらに引用してはいけない。
  記号の定数は `(const zero)` と書く。
- 5.4 の駆動ループ（read-eval-print-loop）は入れていない。scheme13 の REPL の
  中で `read` を回すと、確かめたいものと関係のない入出力の話になる。
  式を1つ渡して `val` を受け取る形にした。
- **Scheme レベルの例外捕捉が無い**ので、演習5.8（ラベルの二重定義）だけは
  `dup_label_error.scm` に分け、終了状態と文面をランナーが見る。
  演習5.30（型の分からない式・手続き）は、評価器の側で `signal-error` に
  値として渡す形にしたので、処理系を止めずにファイル内で主張できる。

### 範囲について

- **5.5.6 は「アドレスの割り出しと引き当て」までを確かめている。**

  `heap-ref` / `heap-set!` を演算表に置いた（本書がレジスタを1本足すのと同じ手）。


## 第5章の演習で分かったこと（25日目に足した分）

24日目は「節の主題が動くか」を見た。25日目は**演習を目的として解いた**。
この2つは処理系にとって別のものを試験する。

**節の主題は「その機構が動くか」だが、演習の多くは「その機構を組み替えられるか」
を問う。** シミュレータの `save`/`restore` の意味を3通りに変える（5.11）、
レジスタをアセンブル時に拾う（5.13）、レジスタに実況を付ける（5.18）——
どれも `set!` で手続きを差し替えて、閉包の作られ方そのものを変える。
命令列をデータとして走査する演習（5.10 の書式変換、5.12 の解析）も同じ筋である。

### 組み替えたときにだけ表に出た誤り（2件・どちらもテスト側）

1. **演習5.17 のラベルは、アセンブル時に決めなければならない。**
   「実行しながら直前のラベルを覚える」形で書いたら、演習5.19 の
   ブレークポイントが2周目で止まらなくなった。繰り返しでラベルへ戻っても
   実行時のカウンタは戻らないためで、**演習が「アセンブラを変えよ」と
   言っている理由がここにある。**

2. **演習5.38（基本演算を開いて埋め込む）で `arg1` の退避を
   `preserving` の外に置いたら、`(+ (* 2 3) (- 10 4))` が 16 になった。**
   2つ目の引数が入れ子の演算だと `arg1` を潰す。`preserving` は
   「前が壊し、かつ後が要る」ものしか退避しないので、**要ることを名簿に
   伝え損ねると黙って壊れる。** 5.5.4 が名簿を持つ設計の値打ちが、
   失敗の側から出た場面。

### 5.5.6 を最後まで通した（演習5.39〜5.44）

24日目は「アドレスの割り出しと引き当て」までだった。25日目に
**翻訳時環境を `compile` の全再帰に通した。** `compile` は3引数のまま残し、
中身を `compile-in`（4引数）に移したので、既存の主張は1つも書き換えていない。

- 演習5.42 — 変数の参照と `set!` がアドレスの命令になる
- 演習5.43 — 本体の先頭の `define` を掃き出し、枠に並べて `set!` に変える。
  内部定義された名前も字句アドレスで引ける
- 演習5.38・5.44 — 基本演算を開いて埋め込む。**名前が隠されていないときだけ**

**scheme13 は 5.5.6 を既定で行っている。** 局所変数は `LD (depth index)`、
大域名だけが `LDG`。この分かれ方が `find-variable` の `not-found` の
分かれ方と1対1で対応する。

### 演習5.45・5.46 — 3通りを同じ計算で並べて測る

同じ `(fact n)` を**専用の機械・翻訳された符号・解釈**で走らせた実測:

| | 押し込み | 最大の深さ |
| --- | --- | --- |
| 専用の機械（5.1.4） | 2n - 2 | 2n - 2 |
| 翻訳された符号（5.5） | 6n - 4 | 3n - 1 |
| 解釈（5.4 の評価器） | 32n - 16 | 3n + 5 |

- **押し込みは 1 : 3 : 16。** 5.5 の冒頭が言う「翻訳は解釈より速い」が数で出る。
- **深さは 2 : 3 : 3。** ここが測って初めて分かった点で、**翻訳と解釈は
  深さの傾きが同じで、差は定数でしかない。** 解釈の高くつく所は
  「要る場所」ではなく「した仕事の量」である。1段ごとに積んでは降ろすものが
  大量にあり、その大半は同じ段の中で解ける。
- 末尾呼び出しは3通りとも成立する。反復のループはどれも定数の深さで回る
  （ただし解釈のほうが定数ぶん深い）。

### 仕様どおりだが引っかかった点

- **有理数が無い。** 演習5.45 で比を `3/2` と書いたら、`(/ 3 2)` が `1` に
  なった（凍結仕様。`(/ 1 3)` は `0`）。実数に落とすか掛け算で比べる。
  **第2章の演習2.38 に続いて2度目**で、どちらも「割り算の結果をそのまま
  比較に使う」場面である。


## 第5章を実ワークロードとして測った（25日目）

第5章は、**開発側の癖の入っていない、外から来た大きなプログラム**である。
5.4 の評価器は 12.96 億命令を実行し、16.5 秒かかる。これを scheme13 自身の
性能の題材にして、VM 命令の実行回数を数えた（`dev_memo.md` の決定57 のやり方。
計測用の複製はスクラッチパッドに置き、`scheme13.cpp` には入れていない）。

| --- | --- | --- | --- | --- |
| `LD` | 24.0% | **26.7%** | **27.5%** | 20.0% |
| `LDG` | 24.6% | 17.3% | 19.1% | 26.7% |
| `APP` | 12.4% | 16.1% | 17.2% | 20.0% |

| `SELR` | 9.2% | 6.9% | 7.1% | 6.7% |

| `RTN` | 5.6% | 5.9% | 5.5% | 0.0% |
| `LDC` | 2.7% | **9.3%** | **7.3%** | 20.0% |

**結論は「新しい当たり所は出なかった」。**

- `LD` + `LDG` はどのワークロードでも 44〜47%、呼び出し（`APP` + `TAPP`）は
  25% 前後。**教科書が書いたプログラムでも比率が動かない。**

「動かす理由が無い」だったら動かさない、というのがこのリポジトリの規律である。
