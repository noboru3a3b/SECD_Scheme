# scheme13 開発メモ

SECD 仮想マシン方式 Scheme 処理系 **scheme13** の開発記録。
`scheme12_bignum_boost_debug.cpp` を土台にした、単一設計者による書き直し。

## 0. この文書の使い方（最初に読むこと）

**この文書は進捗メモではなく、設計の連続性そのものである。**

開発は複数日にまたがるが、各日の作業者（Claude）は前日の記憶を持たない。
したがって「なぜその設計にしたか」がここに書かれていなければ、翌日の作業者は
平気で別の判断をする。それは scheme12 が抱えた「複数の書き手が少しずつ違う
判断をした結果、層が積み重なった状態」を、一人で再生産することを意味する。

### 作業開始時

1. **§1 設計憲章と §2 凍結仕様を必ず読む。** ここは原則として変更しない。
2. §7「現在の状態」で、どこまで動いているかを把握する。
3. §8「次にやること」の先頭から着手する。

### 作業終了時

1. **§6 決定ログに、その日決めたことと理由を追記する。**
   却下した案とその理由も書く。これが最も重要。
2. §7 を現状に合わせて更新する。
3. §8 を書き換える。「次の人が読んで即座に着手できる粒度」で書く。
4. 判断を保留したことは §9 に積む。

### 憲章を変えたくなったら

変えてよい。ただし **§6 に「何を、なぜ変えたか」を必ず残す。**
黙って変えるのが最も避けたい行動。

## 1. 設計憲章（不変の決定）

### 1.1 目的

scheme12 は機能的には完成しているが、複数の書き手の判断が層として積み重なり、
以下のような構造的な澱みが残っている。scheme13 はこれを設計として解消する。

- `Op::LDCT` — コンパイラが一度も生成しない命令が VM に残っている
- `Op::LD` / `Op::LSET` にフレームのベクタ表現とリスト表現が両方生きている
  （「後方互換：リスト形式もサポート」）。最もホットなコードに死んだ分岐がある
- `Op::ARGS` が引数をリストに固め、`APP` が即座にベクタへ戻す（三重変換）
- 文字列型が二重（Scheme 値は `GcString`、シンボル名や `Instruction::sym` は
  `std::string`）で、後者が `GC_MALLOC_UNCOLLECTABLE` からリークする
- `write_newline`（旧API）が `newline` と併存
- ソース中に `// ... (expand_let, ... は以前と同じなので省略)` という
  AI 生成時の足場が残っている

**scheme13 の目的は「新機能」ではなく「同じ振る舞いを、選び直した設計で実現する」
こと。** 機能追加の誘惑に負けないこと。

### 1.2 環境と依存

| 項目 | 決定 |
| --- | --- |
| 開発環境 | VSCode + Dev Container + WSL2（既存の `.devcontainer/` をそのまま使う） |
| 言語 | C++17 |
| GC | Boehm GC（`gc.h` / `gc_cpp.h` / `gc_allocator.h`、`-lgc -lgccpp`） |
| 多倍長整数 | Boost.Multiprecision `cpp_int` |
| これ以外の依存 | **増やさない** |

**理由**: どちらも既に動いていて devcontainer も CI も整っている。ここを
変える理由がなく、変えれば検証コストだけが増える。自前 GC や自前 bignum は
このプロジェクトの主題ではない。

### 1.3 ファイル構成

**単一ファイル `scheme13/scheme13.cpp` とする。** 分割しない。

**理由**: 利用者はこのファイルを単体で AI に渡してレビュー・改修を依頼する
運用をしている。分割するとその運用が壊れる。また既存の Makefile 群が
単一ソースを前提にしている。そもそも scheme12 の問題はファイル数ではなく
「退役させなかった決定が層になったこと」であり、分割は解決策ではない。

代わりに **セクション構造を厳格に守る**（§3 参照）。

**却下案**: `value.hpp` / `reader.cpp` / `compiler.cpp` / `vm.cpp` への分割。
上記の運用上の理由により却下。

### 1.4 三つの優先順位（利用者と合意済み）

1. **既存 `.scm` 資産との互換性が最優先。**
   `system_lib.scm` / `mlib7.scm` / `hashtable_lib.scm` /
   `rbtree_lib_improved.scm` と各テストが**一字も変えずに動く**ことが絶対条件。
   Common Lisp 由来の表面仕様（§2）はそのまま引き継ぐ。R5RS 準拠のために
   表面を変えることはしない。

2. **性能を明示的な設計目標に含める。**
   scheme12 は約 30 万呼び出し/秒。呼び出し規約を最初から設計し直す（§4）。
   これは後から変えにくい部分なので、やるなら最初にやる。

3. **ソース位置つきエラーを実装する。**
   リーダが行・列を記録し、コンパイル時・実行時エラーに位置を添える。
   デバッグ処理系としての価値が最も上がる部分。
   **Scheme レベルの例外機構（`error` / `with-exception-handler` /
   `dynamic-wind`）は入れない。** `dynamic-wind` は継続と絡んで設計が重くなり、
   目的（書き直しによる統一）から外れる。

### 1.5 デバッグ機能は一級市民

`trace-on` / `trace-off` / `compile` / `disassemble` / `globals` / `macros` /
`help` はこの処理系の看板。後付けではなく最初から設計に組み込む。
特に逆アセンブル表示は、命令セットを変えるたびに追随させること。

### 1.6 GC の規律（scheme12 の失敗から）

scheme12 では以下のバグが実際に起きた。同じ轍を踏まないため規律として固定する。

1. **GC ヒープ上のオブジェクトが後始末を要するなら、必ずファイナライザを
   登録する。** `gc` 継承だけではデストラクタが呼ばれない。
   （scheme12 の `FilePort` がこれでディスクリプタを枯渇させた）
   scheme13 では `gc_cleanup` の多重継承ではなく、`make_port()` の中で
   `GC_REGISTER_FINALIZER_IGNORE_SELF` を明示的に呼ぶ形にした（理由は §6 の
   3日目・決定13）。**ポートを作る経路は `make_port()` ただ一つに限ること。**
2. **GC オブジェクトが持つ文字列は必ず `GcString`**
   （`std::basic_string<char, ..., gc_allocator<char>>`）にする。
   `std::string` を持たせると、`gc` 継承クラスのデストラクタが呼ばれないため
   `GC_MALLOC_UNCOLLECTABLE` から確保されたバッファが永久に解放されない。
   （scheme12 の `Symbol::name` / `Instruction::sym` / `Closure::params` が該当）
3. **GC オブジェクトが持つコンテナは `gc_allocator`、GC 管理外のルート
   （グローバル表など）は `traceable_allocator`** を使う。
4. `cpp_int` の limb 配列は `gc_allocator<unsigned long long>` を渡し、
   `GC_DECLARE_PTRFREE(unsigned long long)` を宣言する（保守的 GC の
   偽 retention を防ぐ）。scheme12 の該当コードは正しいので踏襲する。
5. **ファイルを開く関数は `EMFILE`/`ENFILE` で `GC_gcollect()` +
   `GC_invoke_finalizers()` してから1回リトライする。**
   `GC_gcollect()` だけではファイナライザがキューに積まれるだけで実行されない。

## 2. 凍結仕様（互換性契約）

**この節の内容は変更しない。** すべて scheme12（`main` の `88db98b`）で
実測した値。scheme13 はこれらを再現しなければならない。

### 2.1 表示（`write` による）

| 式 | 出力 |
| --- | --- |
| `'()` および `nil` | `NIL` |
| `#t` および `true` | `TRUE` |
| `#f` および `false` | `FALSE` |
| `'AbC` | `AbC` （**シンボルは大小文字を保存する**。上書きしない） |
| `'(a B c)` | `(a B c)` |
| `'(a . b)` | `(a . b)` |
| `'#(1 a "s")` | `#(1 a "s")` |
| `"hi\nthere"` | `"hi` 改行 `there"` （**`write` は改行をエスケープしない**） |
| `(lambda (x y) x)` | `#<closure:(x y)>` |
| `(lambda (x . r) x)` | `#<closure:(x . r)>` |
| `car` | `(PRIMITIVE car)` |
| `if` | `(SPECIAL-FORM if)` |
| 継続 | `#<continuation>` |
| `eof-object` | `#<eof>` |
| 循環リスト（cdr方向） | `(1 . #<circular>)` |
| 循環リスト（car方向） | `(( . #<circular>) 2)` |
| 循環ベクタ | `#(#<circular-vector> 0)` |
| 閉じたポート | `#<closed-port>` |

`display` と `write` の違いは**文字列を引用符で囲むかどうかだけ**。
リストの要素にある文字列は `display` でも引用符つきで出る（`("x" y)`）。

> **注記（4日目に追記）**: この表示は**読み戻せない**。`NIL` / `TRUE` / `FALSE`
> はリーダにとって（小文字の `nil` / `true` / `false` と違い）ただのシンボルなので、
> 書いた出力をもう一度読むと別の値になる。`write` の出力を入力に使う道具
> （`--read` / `--expand` / `tests/compare_expand.sh`）はこの前提で作ること。
> 文字列のエスケープをしない仕様も同じ性質を持つ。

### 2.2 型と述語

- **文字型は存在しない。文字は長さ1の文字列。**
  `(string-ref "abc" 1)` → `"b"`、`(integer->char 65)` → `"A"`
- `eq?` と `eqv?` は同一実装。**数値は値比較**（`(eq? 100000000000 100000000000)`
  → `TRUE`）、シンボルは名前比較、文字列はポインタ比較（`(eq? "a" "a")` → `FALSE`）
- 整数のみ。有理数・実数・複素数はない

### 2.3 算術

- `(/ -7 2)` → `-3`（0方向への切り捨て。`quotient` 相当）
- `(/ x)` は**エラー**:
  `/ requires at least 2 arguments (single-argument reciprocal is not supported; use (/ 1 x) instead)`
- `(modulo -7 2)` → `1`、`(modulo 7 -2)` → `-1`（符号は除数に一致）
- 多倍長: `(* 99999999999 99999999999)` → `9999999999800000000001`

### 2.4 返り値

| 式 | 返り値 |
| --- | --- |
| `(define zz 1)` | シンボル `zz` |
| `(set! v 2)` | 代入した値 `2` |
| `(vector-set! v 0 9)` | `:undef` |
| `(string-set! s 0 "b")` | `:undef` |
| `(display x)` | `x` そのもの |
| `(newline)` | `NIL` |

### 2.5 構文

- **角括弧 `[` `]` は区切り文字ではない。** `'[1 2]` は `[1` と `2]` という
  2つのシンボルとして読まれる（結果として `unbound global: 2]`）
- `#t` / `#f` と `true` / `false` / `nil` のリテラルを両方受け付ける
- `,@` は内部的に `splice` というシンボルに読まれる
  （`unquote-splicing` ではない）
- 準クオートのネスト（`` `(a `(b ,,x)) ``）は未対応。scheme13 でも対応しない
- `define-macro` によるマクロのみ。`syntax-rules` はない

### 2.6 内部 define

本体**先頭**の連続した `define` のみ `letrec` に変換される。
式より後ろの `define`、マクロが生成した `define`、本体先頭の
`(begin (define ...) ...)` のスプライスは**グローバル定義になる**（scheme12 と同じ）。

### 2.7 継続

- `call/cc` と `call-with-current-continuation` の両方を受け付ける
- `call/cc` と `apply` は**特殊形式であって値ではない**。
  `(procedure? call/cc)` → `FALSE`
- トップレベルのフォームは個別に評価されるため、フォームを跨いで継続を
  起動すると、そのフォームの残りは実行されず次のフォームへ進む

## 4. アーキテクチャ方針

### 4.1 呼び出し規約（性能設計の中心）

**scheme12 の問題**: 呼び出し1回につき
`Op::ARGS` が引数をリスト化（n個の Pair + n個の Value を確保）→
`vector_from_list` でベクタへ戻す → `make_vector_value` でフレームをベクタ化、
という三重変換をしていた。加えて `vector_from_list` が呼び出しごとに
`std::unordered_set` をヒープ確保していた（除去実験で約18%改善した）。

**scheme13 の方針**:

- **引数はスタック上に積んだまま `APP` に渡す。** `Op::ARGS` を廃止し、
  `APP` / `TAPP` は引数の個数をオペランドに持つ。フレームはスタックの
  該当区間から直接構築する。リストは一切作らない。
- `apply` のときだけリスト化が必要（`Op::ARGS_AP` 相当）。ここは残す。
- **`SEL` のダンプは `c` と `pc` だけを持つ軽量ノードにする。**
  scheme12 は `s` と `e` を丸ごとコピーしていたが、`JOIN` は `c`/`pc` しか
  使っていなかった。
- ~~ダンプは**不変ノードの永続リンクリスト**（scheme12 の設計を踏襲）。
  継続の捕捉が「先頭ポインタを持つだけ」の O(1) になる。~~
  → **4日目に撤回した。**S を連続スタックにすると捕捉はどのみち O(深さ) に
  なるので、この利点は消える。ダンプは連続配列にする。理由は §4.4.2。
- 循環検出は Floyd の2ポインタ法。ホットパスでハッシュ集合を確保しない。

**目標**: scheme12 の 30 万呼び出し/秒に対し、まず 2〜3 倍を目指す。
ベンチは `(define (loop i acc) (if (= i 0) acc (loop (- i 1) (+ acc 1))))` の
100 万回（scheme12 で約 3.4 秒）。

### 4.2 ソース位置

- リーダは各トークンの行・列を記録し、**ペアと シンボルに位置を持たせる**。
  全 `Value` に持たせるとメモリが増えるので、位置表は
  `Pair*` → `SourcePos` の副表（GC 管理の `unordered_map`）にする案を第一候補とする。
  → **未決定。§9 に保留として記載。**
- エラー表示の形（**7日目の決定33 で確定**。以後この形を崩さない）:

```
Error: mylib.scm:1:1: car: wrong type of argument
  expected: a pair
  given: 5
    (car 5)
    ^
```

  1行目は `位置: 見出し`。見出しは「**誰が**」「**何をしくじったか**」だけを言う。
  2行目以降は字下げ2の**詳細行**で、`expected:` → `given:` の順。
  最後に問題のソース行とキャレット（字下げ4）。

  **見出しの語彙は次に限る。** 増やすときはこの表に足してから使うこと。

  | 見出し | 使うところ |
  | --- | --- |
  | `<who>: wrong type of argument` | 型が違う |
  | `<who>: wrong number of arguments` | 引数の数が違う（クロージャもプリミティブも） |
  | `<who>: index out of range` | 文字列・ベクタへの添字 |
  | `<who>: argument out of range` | 値そのものの範囲（ASCII コード、長さ、乱数の上限） |
  | `bad syntax in <form>` | 構文検査（セクション6/7/8） |
  | `unbound variable: <name>` | 未束縛の参照 |
  | `attempt to call a non-procedure` | 呼べないものを呼んだ |
  | `internal error: <what>` | **処理系自身の不変条件が壊れた。利用者の誤りではない** |

  詳細行のラベルは `expected` / `given` / `note` の3つ。`note` は expected/given に
  当てはまらない補足（未束縛の説明、内部エラーの断り書き）にだけ使う。
  綴りは `detail()` / `expected_given()`（セクション2）に閉じ込め、
  各所で文字列を組み立てない。

- **位置の継承は鎖である**（11日目の決定52）。展開が生んだフォームは位置を
  持たないので、`comp` / `comp_body` は `inherited`（囲みフォームの位置）を
  引き継ぐ。**一箇所でも `nearest_pos` を引き直すと、そこから下が丸ごと位置を
  失う。** `lambda` を作る場所を足すときは、`comp` が解決済みの `pos` を
  必ず渡すこと。回帰は `selftest_macro_positions`。

- **`given:` には「悪い部分そのもの」を出す。** フォーム全体はキャレット行が
  見せている。`(let ((a 1) b) a)` で `given: b` と言えれば、読む側は探さずに済む。

- **前置きは2種類。** REPL は `Error:` を付けて次の入力へ進み、`--load` 中は
  `Fatal error:` を付けて終了コード1で止まる。**読み進めるかどうかの違い**を
  前置きで表す。同じ文面を両方で使う。

### 4.3 再帰の禁止事項

scheme12 では C スタックを溢れさせるバグが2件あった。設計として禁じる。

- **リストの cdr 方向を再帰で辿らない。** `equal?`、`to_string`、`length`、
  `append` などは必ずループにする。car 方向のみ再帰してよい。
- 循環検出の `visited` は「経路上のノード集合」として扱い、
  走査後に自分が入れた分を必ず取り除く（バックトラック）。
  そうしないと共有構造（DAG）を循環と誤判定する。

### 4.4 命令セットと機械の状態（4日目に確定）

**先に紙の上で決めたもの。コードより先にここを読むこと。**

#### 4.4.1 scheme12 の実測から分かった、本当のボトルネック

VM を読み直したところ、`ARGS` の三重変換（§4.1）は**いちばん大きい問題では
なかった**。呼び出し1回あたり、scheme12 は次を全部やっている。

| # | scheme12 がやっていること | 計算量 |
| --- | --- | --- |
| 1 | `ARGS` が引数をリスト化（n個の Pair + n個の Value） | O(n) 確保 |
| 2 | `APP` が `vector_from_list` でベクタへ戻す（`unordered_set` をヒープ確保） | O(n) 確保 |
| 3 | フレームを `Vector` 値にする | 2回の確保 |
| 4 | **`d = dump_push(d, DumpFrame{s, e, c, pc})` で `s` と `e` を丸ごとコピー** | **O(環境の深さ)** |
| 5 | **`new_e = [frame] + clo->captured_env` で環境ベクタを毎回作り直す** | **O(環境の深さ)** |
| 6 | `LDG` が大域変数を**名前で毎回ハッシュ検索** | 参照ごとに1回 |

4・5・6 は §4.1 に書かれていなかった。とくに **4 と 5 は環境の深さに比例する
コピーが呼び出しごとに2回**走る。ベンチのループ本体は `loop` `=` `-` `+` の
4つが大域変数なので、6 だけで**1周あたり4回のハッシュ検索**が入っている。

#### 4.4.2 機械の状態

| 記号 | scheme12 | **scheme13** | 効果 |
| --- | --- | --- | --- |
| S 스택 | `ValueVec` を呼び出しごとに退避・クリア | **単一の連続スタック `ValueVec stack`**。呼び出しは `base` 添字を記録するだけ | コピーが消える |
| E 環境 | フレームの `ValueVec`（呼び出しごとに作り直す） | **フレームの連結リスト `Env*`**。1呼び出し = 1確保 | O(深さ) が O(1) に |
| C コード | `Code*` + `pc` | 同じ | — |
| D ダンプ | 不変ノードの永続リンクリスト（`s`/`e` のコピー入り） | **連続配列 `RootVec<DumpEntry>`**。要素は `{c, pc, env, base}` の POD | 確保が消える |

`Env` は Scheme の値ではないので `Object` を継承しない。**可変長の末尾配列**を
持ち、1フレーム = 1回の `GC_MALLOC` で済ませる。

```
struct Env { Env* next; std::uint32_t size; ValuePtr vals[]; };
```

**却下案 A: ダンプを永続リンクリストのまま残す**（§4.1 の当初の決定）。
理由は「継続の捕捉が先頭ポインタを持つだけの O(1) になる」だったが、
**S を連続スタックにした時点でこの利点は消える**。捕捉はスタックの生存区間を
コピーせざるを得ず O(深さ) になるので、ダンプだけ O(1) でも意味がない。
連続配列なら呼び出しごとの確保がゼロになる。§4.1 のこの一文は 4日目に撤回した。

**却下案 B: `if` を SEL/JOIN でなくジャンプ命令にする。** `if` 1回あたりの
ダンプ操作が完全に消えるので速いが、(a) SECD 機械としての性質（D が制御の
退避先である）が薄れる、(b) 逆アセンブル表示が入れ子でなくラベル付きの
平坦な列になり §1.5 の看板機能が読みにくくなる。
連続配列ダンプにした時点で SEL の push は「配列に16バイト積む」だけなので、
残る差は小さいと判断して却下。**性能が足りなければ最初に見直す候補はここ。**

#### 4.4.3 継続

`call/cc` は S とダンプ配列の**スナップショットをコピーして持つ**。
起動時は書き戻す。ダンプの `base` は添字なので、コピーしても整合する。
環境（`Env*`）はコピーせず共有する — `set!` が捕捉をまたいで見えるのは
正しい意味論で、scheme12 も（フレームの実体は共有していたので）同じだった。

捕捉のコストは O(スタックの深さ)。call/cc はホットパスではないので許容する。

#### 4.4.4 大域変数は「セル」で持つ

**`LDG` / `GSET` / `DEF` は名前でなく `GlobalCell*` をオペランドに持つ。**
コンパイル時に `global_cell(name)` でセルを作る（未定義でも作る）。
実行時は 1回のロードと未束縛チェックだけ。ハッシュ検索が消える。

```
struct GlobalCell { ValuePtr value;  // nullptr なら未束縛
                    ValuePtr macro;  // マクロなら変換子、それ以外は nullptr
                    GcString name; };
```

`g_globals` と `g_macros` の2表（scheme12）を**1つのセルに統合**する。
原典がシンボルのプロパティリスト1箇所に両方入れて car で見分けていたのと
同じ構造に戻る（`micro_scheme8_notes.md` §3.3）。前方参照は、未束縛のセルを
先に作っておけば自然に解決する。

#### 4.4.5 命令セット

`Op::ARGS` は**無い**（引数はスタックに積んだまま）。`Op::LDCT` も**無い**（決定7）。

| 命令 | オペランド | 動作 |
| --- | --- | --- |
| `LD` | a=フレーム番号, b=位置 | 局所変数を積む。環境を a 回辿る |
| `LDC` | p1=定数 | 定数を積む |
| `LDG` | p1=`GlobalCell*` | 大域変数を積む。未束縛ならエラー |
| `LDF` | p1=`Template*`, b=使い捨ての印 | 雛形と現在の環境からクロージャを作って積む。**b=1 なら「直後の `APP` に消費されて即座に死ぬ」印**で、VM は確保せずスクラッチを使い回す（12日目の決定54） |
| `APP` | a=引数の個数 | スタック上の `arg0 .. arg_{n-1} callee` を呼ぶ。ダンプを積む |
| `TAPP` | a=引数の個数 | 同上。ダンプを積まない（末尾呼び出し） |
| `ARGS_AP` | a=個数 | `apply` 用。末尾のリストと手前の a-1 個を1つのリストにまとめる |
| `APPLY` / `TAPPLY` | — | `apply` 用。callee と引数リストを取り出して呼ぶ |
| `RTN` | — | ダンプを1つ戻す。空なら実行終了 |
| `SEL` | p1=真の枝, p2=偽の枝 | 分岐。ダンプに戻り先を積む |
| `SELR` | p1=真の枝, p2=偽の枝 | 末尾位置の分岐。ダンプを積まない |
| `JOIN` | — | `SEL` の戻り先へ帰る |
| `POP` | — | 1つ捨てる |
| `DEF` | p1=`GlobalCell*` | 大域定義。**シンボルを残す**（§2.4） |
| `DEFM` | p1=`GlobalCell*` | マクロ定義。セルの `macro` 側に入れる |
| `LSET` | a, b | 局所変数への代入。**代入した値を残す**（§2.4） |
| `GSET` | p1=`GlobalCell*` | 大域変数への代入。同上 |
| `CALLCC` / `TCALLCC` | — | 継続を作って、積んである関数に適用する |
| `STOP` | — | 実行終了 |

**呼び出しの約束**: `APP n` の時点でスタックは下から
`... arg0 arg1 ... arg_{n-1} callee` の順（**callee が一番上**）。

> **5日目に訂正**: ここは当初「callee が先（下）」と書いていたが、
> **scheme12 は引数を左から順に評価してから最後に演算子を評価する**
> （`comp` が `for(args) comp(a); ARGS; comp(head); APP` の順に出す）。
> 評価順はスタックの順序そのものなので、callee を下にすると
> `((begin (display "f") car) (begin (display "a") '(1)))` のような式の
> 出力順が変わる。§1.4 の優先順位1（既存資産とバイト単位で同じ出力）を
> 守るため、**評価順は scheme12 のまま**にし、callee を一番上に置く。
> 引数は `[sp-1-n, sp-1)` の区間にあるので、フレームの切り出しは同じく素直。

`apply` だけは引数の個数がコンパイル時に決まらないので、`ARGS_AP` で
リストにまとめてから `APPLY` / `TAPPLY` で呼ぶ（§4.1 の「apply のときだけ
リスト化が必要」）。`APP` に動的な個数を渡す方式は、callee の評価中に
別の `apply` が走ると個数を保持する場所が壊れるので採らない。

#### 4.4.6 `Instruction` の持ち方（§9 の保留を解消）

**固定長 32 バイトの構造体。**汎用のポインタ枠を2つ持ち、意味は命令ごとに
上の表で決める（型付きのアクセサ関数を1箇所だけ用意し、キャストはそこに閉じる）。

```
struct Instruction {
    Op            op;    // 1
    std::uint16_t a, b;  // フレーム番号 / 位置 / 引数の個数
    SourcePos     pos;   // 実行時エラーに位置を添えるため（§1.4 の優先順位3）
    void*         p1;
    void*         p2;
};
```

却下案: `std::variant` / 命令種別ごとの副表。前者は最大要素に合わせて太り、
後者は逆アセンブルとトレースが2箇所を引き回すことになる。
scheme12 の 100バイト超（`std::string` + `std::vector<std::string>` +
`optional<std::string>` が常に同居）に比べれば固定長32バイトで十分小さい。

`LDF` の `Template` はコンパイル時に1個だけ作る:

```
struct Template { GcVec<GcString> params; std::optional<GcString> rest;
                  Code* body; GcString name; };
```

`LDF` の実行は「雛形と現在の環境を束ねる」だけになり、クロージャ生成のたびに
仮引数名の配列を複製しない（scheme12 は `lambda_params` を毎回コピーしていた）。

### 2026-09-04（3日目）— 値モデル・表示・リーダ（セクション 1〜5）

`scheme13/scheme13.cpp` の実装に着手。セクション 1〜5 が動き、
`make -C scheme13 selftest` が **58 checks, 0 failed**。

**決めたこと**

9. **値モデルは「タグ付き基底クラス + 継承」にする。**
   `Object`（tag + ソース位置、12バイト）を各型が継承し、値は `Object*` 一本。
   却下案: scheme12 の `Value{std::variant<...>}` + 実体を別確保する二段構え。
   理由: (a) cons 1個が 2回の確保・56バイトから **1回の確保・32バイト**になる。
   (b) variant は最大要素（32バイトの文字列）に合わせて全 Value が太る。
   (c) ヘッダの詰め物にソース位置がちょうど収まる（決定12）。
   なお **`nullptr` は値ではない**。空リストは必ずシングルトン `g_nil`。
   scheme12 は `is_nil(nullptr)` を真としていたが、これは「うっかり nullptr が
   混ざっても気づけない」設計なので引き継がない。

10. **小さい整数はポインタに埋め込む（即値 fixnum）。**
    最下位ビットが 1 なら整数（62bit + 符号）、0 ならヒープオブジェクト。
    `(+ acc 1)` が 1回も確保しなくなる。§4.1 のベンチが最も効く場所で、
    しかも**後から入れると算術プリミティブを全部書き直すことになる**ので今決めた。
    保守的 GC との相性: 奇数のビット列は「ヒープ内部を指すように見える」ことで
    偽 retention を起こしうるだけで、破壊は起きない。
    却下案: scheme12 どおり全整数を `BigInt` オブジェクトにする（単純だが、
    ベンチのループが毎回 2回確保する）。
    **制約**: bignum 演算の結果が fixnum に収まったら必ず fixnum に落とすこと。
    これを守らないと §2.2 の「数値は値比較」が表現によってぶれる。→ §9 に記載。

11. **プリミティブは `std::function` ではなく素の関数ポインタ
    `ValuePtr(*)(ValuePtr* argv, std::size_t argc)`。**
    理由: (a) `std::function` はキャプチャを持つと `::operator new`
    （libgccpp 経由で `GC_MALLOC_UNCOLLECTABLE`）から確保し、`gc` 継承クラスの
    デストラクタは呼ばれないので解放されない（§1.6-2 と同じ穴）。
    (b) §4.1 の「引数をスタック上に積んだまま渡す」が、そのまま
    `(argv, argc)` として書ける。scheme12 は呼び出しごとに `ValueVec` へ
    詰め替えていた。

12. **ソース位置はオブジェクトのヘッダに埋める**（§9 の保留を解消）。
    却下案: `Pair*` → `SourcePos` の副表。理由: **キーが強参照になるので、
    読み込んだペアが永久に回収されない**。これは「気づかないうちに溜まる」
    たぐいの問題で、今回いちばん避けたいもの。ヘッダ埋め込みなら、tag の後ろに
    どのみち入る詰め物に col/file/line が収まり、ペア1個あたりの増分は
    16バイト、参照はハッシュ引きでなくフィールド読み出しで済む。
    - 位置を持つのは**リーダが作ったオブジェクトだけ**。実行時に cons した
      ペアの位置は 0（＝位置なし）。
    - **アトムは位置を持たない**。シンボルはインターンされて共有されるので
      持てず、fixnum は即値でヘッダが無い。エラーは「一番近い、位置を持つ
      囲みフォーム」を指す（`nearest_pos`）。リストの各ペアには自分の car に
      あたる要素の位置を、先頭のペアには `(` の位置を入れてある。
    - ソースは全文を `g_sources` に保持する（キャレット行を描くため）。
      REPL の入力は 1 回ごとに別のソースとして登録する。同じ枠を使い回すと、
      前の入力で作られたクロージャのエラーが今の入力の行を指してしまう。
      ファイル id は 16bit なので上限 65535、超えたら位置なしに落とす。

13. **ポートのファイナライザは `make_port()` で明示登録する。**
    `Object` が既に `gc` を継承しているため `gc_cleanup` を多重継承すると
    `operator new` が曖昧になる。`GC_REGISTER_FINALIZER_IGNORE_SELF` を
    `make_port()` の中で呼ぶ（gc_cleanup が内部でやっているのと同じこと）。
    **ポートを作る経路は `make_port()` ただ一つに限ること。** ここを迂回すると
    §1.6-1 のディスクリプタ枯渇がそのまま再発する。

52. **`compile_lambda` は `comp` が解決済みの位置を受け取る。**
    - 症状: マクロが `lambda` を含むフォームへ展開すると、**その本体で
      起きたエラーが位置を丸ごと失う**。`Fatal error:` の後にファイル名も
      行番号もキャレット行も出ない
    - 原因: `comp` は `pos = nearest_pos(expr)`、無ければ `inherited` という
      二段構えで位置を決めているのに、`compile_lambda` が
      **`nearest_pos(whole)` を引き直していた**。展開が生んだ `lambda`
      フォームは位置を持たないので、そこで `inherited` が捨てられ、
      本体以下が丸ごと位置なしになる
    - 修正: `compile_lambda` に `inherited` を渡し、
      `nearest_pos(whole)` が不明なときはそれを使う。呼び出しは
      `comp` の中の2箇所（`lambda` と `(define (f ...) ...)`）で、
      どちらも解決済みの `pos` を渡せる
    - `comp_body` の空本体も `SourcePos{}` ではなく `inherited` を積むようにした
    - **これは `let` / `cond` / `do` / 名前つき `let` / 内部 define など
      「lambda に落ちる構文」すべてに効く。** ただし普通のソースでは本体の
      フォーム自身が位置を持つので、症状が出るのは展開が生んだ本体だけだった
    - **教訓: 位置の継承は鎖であって、一箇所でも `nearest_pos` を引き直すと
      そこから下が丸ごと落ちる。** `lambda` を作る場所を足すときは、
      `comp` が解決済みの `pos` を必ず渡すこと（§4.2 に追記した）

## 9. 保留・未解決の問い

- ~~**ソース位置の持たせ方**~~ → 3日目の決定12 で解決（ヘッダに埋め込む）。

- **算術の fixnum / bignum 境界**（決定10 の帰結）。**規律として守り続けること**:
  - fixnum どうしの演算は `__builtin_*_overflow` で検査し、溢れたら bignum へ
  - **bignum 演算の結果が fixnum に収まったら必ず fixnum に落とす**
    （`make_int(const BigInt&)` が既にそうしている。専用の経路を増やさないこと）
  - これを破ると §2.2「数値は値比較」が表現によってぶれ、`eq?` の結果が変わる
  → `--selftest` の `selftest_eval` に境界のテストを入れてある（"fixnum overflow"
    と "normalize back"）。算術を触ったら必ず通すこと。
  → この帰結として `memq` / `assq` は scheme12 と結果が違う（決定28）。

- ~~**環境フレームの表現**~~ → 4日目の決定17（§4.4.2）で解決、5日目に実装。
  フレームの連結リスト `Env*`、可変長末尾配列で1フレーム=1確保。

- **標準ポートの差し替え**（10日目の決定46・48 の帰結）。いま
  `(current-output-port)` は固定で、`with-output-to-file` のような動的な
  差し替えが無い。既定の出力先はすべて `g_stdout_port` を経由しているので
  差し替え自体は1箇所で済む。
  → **13日目に半分解けた。**「継続で外へ跳んだときに元へ戻す責任」は
  `dynamic-wind`（決定59）が持てる。残るのは
