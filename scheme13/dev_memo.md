# scheme13 開発メモ

SECD 仮想マシン方式 Scheme 処理系 **scheme13** の開発記録。
`scheme12_bignum_boost_debug.cpp` を土台にした、単一設計者による書き直し。

## 0. この文書の使い方（最初に読むこと）

**この文書は進捗メモではなく、設計の連続性そのものである。**

開発は複数日にまたがるが、各日の作業者（Claude）は前日の記憶を持たない。
したがって「なぜその設計にしたか」がここに書かれていなければ、翌日の作業者は
平気で別の判断をする。それは scheme12 が抱えた「複数の書き手が少しずつ違う
判断をした結果、層が積み重なった状態」を、一人で再生産することを意味する。

### 作業開始時

1. **§1 設計憲章と §2 凍結仕様を必ず読む。** ここは原則として変更しない。
2. §7「現在の状態」で、どこまで動いているかを把握する。
3. §8「次にやること」の先頭から着手する。

### 作業終了時

1. **§6 決定ログに、その日決めたことと理由を追記する。**
   却下した案とその理由も書く。これが最も重要。
2. §7 を現状に合わせて更新する。
3. §8 を書き換える。「次の人が読んで即座に着手できる粒度」で書く。
4. 判断を保留したことは §9 に積む。

### 憲章を変えたくなったら

変えてよい。ただし **§6 に「何を、なぜ変えたか」を必ず残す。**
黙って変えるのが最も避けたい行動。

## 1. 設計憲章（不変の決定）

### 1.1 目的

scheme12 は機能的には完成しているが、複数の書き手の判断が層として積み重なり、
以下のような構造的な澱みが残っている。scheme13 はこれを設計として解消する。

- `Op::LDCT` — コンパイラが一度も生成しない命令が VM に残っている
- `Op::LD` / `Op::LSET` にフレームのベクタ表現とリスト表現が両方生きている
  （「後方互換：リスト形式もサポート」）。最もホットなコードに死んだ分岐がある
- `Op::ARGS` が引数をリストに固め、`APP` が即座にベクタへ戻す（三重変換）
- 文字列型が二重（Scheme 値は `GcString`、シンボル名や `Instruction::sym` は
  `std::string`）で、後者が `GC_MALLOC_UNCOLLECTABLE` からリークする
- `write_newline`（旧API）が `newline` と併存
- ソース中に `// ... (expand_let, ... は以前と同じなので省略)` という
  AI 生成時の足場が残っている

**scheme13 の目的は「新機能」ではなく「同じ振る舞いを、選び直した設計で実現する」
こと。** 機能追加の誘惑に負けないこと。

### 1.2 環境と依存

| 項目 | 決定 |
| --- | --- |
| 開発環境 | VSCode + Dev Container + WSL2（既存の `.devcontainer/` をそのまま使う） |
| 言語 | C++17 |
| GC | Boehm GC（`gc.h` / `gc_cpp.h` / `gc_allocator.h`、`-lgc -lgccpp`） |
| 多倍長整数 | Boost.Multiprecision `cpp_int` |
| これ以外の依存 | **増やさない** |

**理由**: どちらも既に動いていて devcontainer も CI も整っている。ここを
変える理由がなく、変えれば検証コストだけが増える。自前 GC や自前 bignum は
このプロジェクトの主題ではない。

### 1.3 ファイル構成

**単一ファイル `scheme13/scheme13.cpp` とする。** 分割しない。

**理由**: 利用者はこのファイルを単体で AI に渡してレビュー・改修を依頼する
運用をしている。分割するとその運用が壊れる。また既存の Makefile 群が
単一ソースを前提にしている。そもそも scheme12 の問題はファイル数ではなく
「退役させなかった決定が層になったこと」であり、分割は解決策ではない。

代わりに **セクション構造を厳格に守る**（§3 参照）。

**却下案**: `value.hpp` / `reader.cpp` / `compiler.cpp` / `vm.cpp` への分割。
上記の運用上の理由により却下。

### 1.4 三つの優先順位（利用者と合意済み）

1. **既存 `.scm` 資産との互換性が最優先。**
   `system_lib.scm` / `mlib7.scm` / `hashtable_lib.scm` /
   `rbtree_lib_improved.scm` と各テストが**一字も変えずに動く**ことが絶対条件。
   Common Lisp 由来の表面仕様（§2）はそのまま引き継ぐ。R5RS 準拠のために
   表面を変えることはしない。

2. **性能を明示的な設計目標に含める。**
   scheme12 は約 30 万呼び出し/秒。呼び出し規約を最初から設計し直す（§4）。
   これは後から変えにくい部分なので、やるなら最初にやる。

3. **ソース位置つきエラーを実装する。**
   リーダが行・列を記録し、コンパイル時・実行時エラーに位置を添える。
   デバッグ処理系としての価値が最も上がる部分。
   **Scheme レベルの例外機構（`error` / `with-exception-handler` /
   `dynamic-wind`）は入れない。** `dynamic-wind` は継続と絡んで設計が重くなり、
   目的（書き直しによる統一）から外れる。

### 1.5 デバッグ機能は一級市民

`trace-on` / `trace-off` / `compile` / `disassemble` / `globals` / `macros` /
`help` はこの処理系の看板。後付けではなく最初から設計に組み込む。
特に逆アセンブル表示は、命令セットを変えるたびに追随させること。

### 1.6 GC の規律（scheme12 の失敗から）

scheme12 では以下のバグが実際に起きた。同じ轍を踏まないため規律として固定する。

1. **GC ヒープ上のオブジェクトが後始末を要するなら、必ずファイナライザを
   登録する。** `gc` 継承だけではデストラクタが呼ばれない。
   （scheme12 の `FilePort` がこれでディスクリプタを枯渇させた）
   scheme13 では `gc_cleanup` の多重継承ではなく、`make_port()` の中で
   `GC_REGISTER_FINALIZER_IGNORE_SELF` を明示的に呼ぶ形にした（理由は §6 の
   3日目・決定13）。**ポートを作る経路は `make_port()` ただ一つに限ること。**
2. **GC オブジェクトが持つ文字列は必ず `GcString`**
   （`std::basic_string<char, ..., gc_allocator<char>>`）にする。
   `std::string` を持たせると、`gc` 継承クラスのデストラクタが呼ばれないため
   `GC_MALLOC_UNCOLLECTABLE` から確保されたバッファが永久に解放されない。
   （scheme12 の `Symbol::name` / `Instruction::sym` / `Closure::params` が該当）
3. **GC オブジェクトが持つコンテナは `gc_allocator`、GC 管理外のルート
   （グローバル表など）は `traceable_allocator`** を使う。
4. `cpp_int` の limb 配列は `gc_allocator<unsigned long long>` を渡し、
   `GC_DECLARE_PTRFREE(unsigned long long)` を宣言する（保守的 GC の
   偽 retention を防ぐ）。scheme12 の該当コードは正しいので踏襲する。
5. **ファイルを開く関数は `EMFILE`/`ENFILE` で `GC_gcollect()` +
   `GC_invoke_finalizers()` してから1回リトライする。**
   `GC_gcollect()` だけではファイナライザがキューに積まれるだけで実行されない。

### 2.2 型と述語

- **文字型は存在しない。文字は長さ1の文字列。**
  `(string-ref "abc" 1)` → `"b"`、`(integer->char 65)` → `"A"`
- `eq?` と `eqv?` は同一実装。**数値は値比較**（`(eq? 100000000000 100000000000)`
  → `TRUE`）、シンボルは名前比較、文字列はポインタ比較（`(eq? "a" "a")` → `FALSE`）
- **正確な整数と、不正確な実数の2種類**（18日目に改訂。決定81）。
  整数は即値 fixnum とヒープ Bignum、実数は IEEE 754 の倍精度（binary64）。
  **有理数と複素数は無い。** `(/ 7 2)` が `7/2` になることはない（決定82）
- `eqv?` は**正確さが一致して初めて真**（決定86）。上の「数値は値比較」は
  **同じ正確さどうしの話**で、そこは1つも変わらない。
  `(= 1 1.0)` → `TRUE` だが `(eqv? 1 1.0)` → `FALSE`。
  実数どうしの `eqv?` はビット列で比べるので `(eqv? 0.0 -0.0)` → `FALSE`、
  `(eqv? +nan.0 +nan.0)` → `TRUE`（`=` のほうは逆に `TRUE` / `FALSE`）
- 実数の結果は**整数に落とさない**。`(* 2.0 3.0)` は `6.0` であって `6` ではない
  （決定85。整数側の「表現をひとつに正規化する」規律と**向きが逆**。§9 を読むこと）

### 2.3 算術

- `(/ -7 2)` → `-3`（0方向への切り捨て。`quotient` 相当）。
  **引数がすべて正確な整数のときの `/` は今までどおり**（18日目に利用者が選択。決定82）
- `(/ x)` は**エラー**:
  `/ requires at least 2 arguments (single-argument reciprocal is not supported; use (/ 1 x) instead)`
  **引数の型によらずエラー**。`(/ 2.0)` も同じ（型で arity を変えない）
- `(modulo -7 2)` → `1`、`(modulo 7 -2)` → `-1`（符号は除数に一致）
- 多倍長: `(* 99999999999 99999999999)` → `9999999999800000000001`

**実数が混ざったとき（18日目に追加）**

- **伝播規則: 引数に不正確な数が1つでもあれば、結果も不正確**（決定91）。
  `(+ 1 1.5)` → `2.5`、`(/ 7 2.0)` → `3.5`、`(* 2 3.0)` → `6.0`
- `(/ 1 3)` → **`0`**。SICP のような実数前提のコードは `(/ 1.0 3)` あるいは
  `(exact->inexact ...)` と書く。**これは仕様であって不具合ではない**（決定82）
- 比較（`=` `<` `>` `<=` `>=`）に NaN が混ざったら**どの比較も偽**（決定87）。
  `(< +nan.0 1)` も `(>= +nan.0 1)` も `FALSE`。
  **`>=` を「`<` の否定」で書かないこと**
- 整数と実数の比較は整数を倍精度に寄せる。**2^53 を超える整数では桁が落ちる**
  （決定88。正確に比べるには有理数が要るので、そこは入れない）
- **整数を要求する場所は実数を受け取らない**（決定92）。添字・長さ・文字コード・
  `modulo` / `quotient` / `remainder` / `even?` / `odd?` はすべて
  `wrong type of argument` + `expected: an integer` で弾く。`(vector-ref v 1.0)` はエラー
- 0除算: `(/ 1 0)` はエラーのまま。`(/ 1.0 0.0)` は `+inf.0`
  （**実数の除算は IEEE 754 に従い、例外にしない**）

### 2.5 構文

- **角括弧 `[` `]` は区切り文字ではない。** `'[1 2]` は `[1` と `2]` という
  2つのシンボルとして読まれる（結果として `unbound global: 2]`）
- `#t` / `#f` と `true` / `false` / `nil` のリテラルを両方受け付ける
- `,@` は内部的に `splice` というシンボルに読まれる
  （`unquote-splicing` ではない）
- 準クオートのネスト（`` `(a `(b ,,x)) ``）は未対応。scheme13 でも対応しない
- `define-macro` によるマクロのみ。`syntax-rules` はない
- 実数のリテラル（18日目に追加。決定89）。**トークン全体が形に一致したときだけ数**で、
  外れたものは今までどおりシンボルになる
  - `1.5` `-0.75` `.5` `1.` `1e10` `1.5e-3` `+2.5E7`
  - `+inf.0` / `-inf.0` / `+nan.0` / `-nan.0`（R7RS の綴り）
  - `1/2` `1.2.3` `1e` は**シンボル**（有理数は無い。§2.2）
  - ドット対とは衝突しない。`.` がドットになるのは次が区切り文字のときだけなので、
    `(a .5)` は `a` と `0.5` の2要素、`(a . 5)` はドット対

### 2.6 内部 define

本体**先頭**の連続した `define` のみ `letrec` に変換される。
式より後ろの `define`、マクロが生成した `define`、本体先頭の
`(begin (define ...) ...)` のスプライスは**グローバル定義になる**（scheme12 と同じ）。

### 2.7 継続

- `call/cc` と `call-with-current-continuation` の両方を受け付ける
- `call/cc` と `apply` は**特殊形式であって値ではない**。
  `(procedure? call/cc)` → `FALSE`
- トップレベルのフォームは個別に評価されるため、フォームを跨いで継続を
  起動すると、そのフォームの残りは実行されず次のフォームへ進む

## 4. アーキテクチャ方針

### 4.1 呼び出し規約（性能設計の中心）

**scheme12 の問題**: 呼び出し1回につき
`Op::ARGS` が引数をリスト化（n個の Pair + n個の Value を確保）→
`vector_from_list` でベクタへ戻す → `make_vector_value` でフレームをベクタ化、
という三重変換をしていた。加えて `vector_from_list` が呼び出しごとに
`std::unordered_set` をヒープ確保していた（除去実験で約18%改善した）。

**scheme13 の方針**:

- **引数はスタック上に積んだまま `APP` に渡す。** `Op::ARGS` を廃止し、
  `APP` / `TAPP` は引数の個数をオペランドに持つ。フレームはスタックの
  該当区間から直接構築する。リストは一切作らない。
- `apply` のときだけリスト化が必要（`Op::ARGS_AP` 相当）。ここは残す。
- **`SEL` のダンプは `c` と `pc` だけを持つ軽量ノードにする。**
  scheme12 は `s` と `e` を丸ごとコピーしていたが、`JOIN` は `c`/`pc` しか
  使っていなかった。
- ~~ダンプは**不変ノードの永続リンクリスト**（scheme12 の設計を踏襲）。
  継続の捕捉が「先頭ポインタを持つだけ」の O(1) になる。~~
  → **4日目に撤回した。**S を連続スタックにすると捕捉はどのみち O(深さ) に
  なるので、この利点は消える。ダンプは連続配列にする。理由は §4.4.2。
- 循環検出は Floyd の2ポインタ法。ホットパスでハッシュ集合を確保しない。

**目標**: scheme12 の 30 万呼び出し/秒に対し、まず 2〜3 倍を目指す。
ベンチは `(define (loop i acc) (if (= i 0) acc (loop (- i 1) (+ acc 1))))` の
100 万回（scheme12 で約 3.4 秒）。

### 4.2 ソース位置

- リーダは各トークンの行・列を記録し、**ペアと シンボルに位置を持たせる**。
  全 `Value` に持たせるとメモリが増えるので、位置表は
  `Pair*` → `SourcePos` の副表（GC 管理の `unordered_map`）にする案を第一候補とする。
  → **未決定。§9 に保留として記載。**
- エラー表示の形（**7日目の決定33 で確定**。以後この形を崩さない）:

```
Error: mylib.scm:1:1: car: wrong type of argument
  expected: a pair
  given: 5
    (car 5)
    ^
```

  1行目は `位置: 見出し`。見出しは「**誰が**」「**何をしくじったか**」だけを言う。
  2行目以降は字下げ2の**詳細行**で、`expected:` → `given:` の順。
  最後に問題のソース行とキャレット（字下げ4）。

  **見出しの語彙は次に限る。** 増やすときはこの表に足してから使うこと。

  | 見出し | 使うところ |
  | --- | --- |
  | `<who>: wrong type of argument` | 型が違う |
  | `<who>: wrong number of arguments` | 引数の数が違う（クロージャもプリミティブも） |
  | `<who>: index out of range` | 文字列・ベクタへの添字 |
  | `<who>: argument out of range` | 値そのものの範囲（ASCII コード、長さ、乱数の上限） |
  | `bad syntax in <form>` | 構文検査（セクション6/7/8） |
  | `unbound variable: <name>` | 未束縛の参照 |
  | `attempt to call a non-procedure` | 呼べないものを呼んだ |
  | `internal error: <what>` | **処理系自身の不変条件が壊れた。利用者の誤りではない** |

  詳細行のラベルは `expected` / `given` / `note` の3つ。`note` は expected/given に
  当てはまらない補足（未束縛の説明、内部エラーの断り書き）にだけ使う。
  綴りは `detail()` / `expected_given()`（セクション2）に閉じ込め、
  各所で文字列を組み立てない。

- **位置の継承は鎖である**（11日目の決定52）。展開が生んだフォームは位置を
  持たないので、`comp` / `comp_body` は `inherited`（囲みフォームの位置）を
  引き継ぐ。**一箇所でも `nearest_pos` を引き直すと、そこから下が丸ごと位置を
  失う。** `lambda` を作る場所を足すときは、`comp` が解決済みの `pos` を
  必ず渡すこと。回帰は `selftest_macro_positions`。

- **`given:` には「悪い部分そのもの」を出す。** フォーム全体はキャレット行が
  見せている。`(let ((a 1) b) a)` で `given: b` と言えれば、読む側は探さずに済む。

- **前置きは2種類。** REPL は `Error:` を付けて次の入力へ進み、`--load` 中は
  `Fatal error:` を付けて終了コード1で止まる。**読み進めるかどうかの違い**を
  前置きで表す。同じ文面を両方で使う。

### 4.3 再帰の禁止事項

scheme12 では C スタックを溢れさせるバグが2件あった。設計として禁じる。

- **リストの cdr 方向を再帰で辿らない。** `equal?`、`to_string`、`length`、
  `append` などは必ずループにする。car 方向のみ再帰してよい。
- 循環検出の `visited` は「経路上のノード集合」として扱い、
  走査後に自分が入れた分を必ず取り除く（バックトラック）。
  そうしないと共有構造（DAG）を循環と誤判定する。

### 4.4 命令セットと機械の状態（4日目に確定）

**先に紙の上で決めたもの。コードより先にここを読むこと。**

#### 4.4.1 scheme12 の実測から分かった、本当のボトルネック

VM を読み直したところ、`ARGS` の三重変換（§4.1）は**いちばん大きい問題では
なかった**。呼び出し1回あたり、scheme12 は次を全部やっている。

| # | scheme12 がやっていること | 計算量 |
| --- | --- | --- |
| 1 | `ARGS` が引数をリスト化（n個の Pair + n個の Value） | O(n) 確保 |
| 2 | `APP` が `vector_from_list` でベクタへ戻す（`unordered_set` をヒープ確保） | O(n) 確保 |
| 3 | フレームを `Vector` 値にする | 2回の確保 |
| 4 | **`d = dump_push(d, DumpFrame{s, e, c, pc})` で `s` と `e` を丸ごとコピー** | **O(環境の深さ)** |
| 5 | **`new_e = [frame] + clo->captured_env` で環境ベクタを毎回作り直す** | **O(環境の深さ)** |
| 6 | `LDG` が大域変数を**名前で毎回ハッシュ検索** | 参照ごとに1回 |

4・5・6 は §4.1 に書かれていなかった。とくに **4 と 5 は環境の深さに比例する
コピーが呼び出しごとに2回**走る。ベンチのループ本体は `loop` `=` `-` `+` の
4つが大域変数なので、6 だけで**1周あたり4回のハッシュ検索**が入っている。

#### 4.4.2 機械の状態

| 記号 | scheme12 | **scheme13** | 効果 |
| --- | --- | --- | --- |
| S 스택 | `ValueVec` を呼び出しごとに退避・クリア | **単一の連続スタック `ValueVec stack`**。呼び出しは `base` 添字を記録するだけ | コピーが消える |
| E 環境 | フレームの `ValueVec`（呼び出しごとに作り直す） | **フレームの連結リスト `Env*`**。1呼び出し = 1確保 | O(深さ) が O(1) に |
| C コード | `Code*` + `pc` | 同じ | — |
| D ダンプ | 不変ノードの永続リンクリスト（`s`/`e` のコピー入り） | **連続配列 `RootVec<DumpEntry>`**。要素は `{c, pc, env, base}` の POD | 確保が消える |

`Env` は Scheme の値ではないので `Object` を継承しない。**可変長の末尾配列**を
持ち、1フレーム = 1回の `GC_MALLOC` で済ませる。

```
struct Env { Env* next; std::uint32_t size; ValuePtr vals[]; };
```

**却下案 A: ダンプを永続リンクリストのまま残す**（§4.1 の当初の決定）。
理由は「継続の捕捉が先頭ポインタを持つだけの O(1) になる」だったが、
**S を連続スタックにした時点でこの利点は消える**。捕捉はスタックの生存区間を
コピーせざるを得ず O(深さ) になるので、ダンプだけ O(1) でも意味がない。
連続配列なら呼び出しごとの確保がゼロになる。§4.1 のこの一文は 4日目に撤回した。

**却下案 B: `if` を SEL/JOIN でなくジャンプ命令にする。** `if` 1回あたりの
ダンプ操作が完全に消えるので速いが、(a) SECD 機械としての性質（D が制御の
退避先である）が薄れる、(b) 逆アセンブル表示が入れ子でなくラベル付きの
平坦な列になり §1.5 の看板機能が読みにくくなる。
連続配列ダンプにした時点で SEL の push は「配列に16バイト積む」だけなので、
残る差は小さいと判断して却下。**性能が足りなければ最初に見直す候補はここ。**

#### 4.4.3 継続

`call/cc` は S とダンプ配列の**スナップショットをコピーして持つ**。
起動時は書き戻す。ダンプの `base` は添字なので、コピーしても整合する。
環境（`Env*`）はコピーせず共有する — `set!` が捕捉をまたいで見えるのは
正しい意味論で、scheme12 も（フレームの実体は共有していたので）同じだった。

捕捉のコストは O(スタックの深さ)。call/cc はホットパスではないので許容する。

#### 4.4.4 大域変数は「セル」で持つ

**`LDG` / `GSET` / `DEF` は名前でなく `GlobalCell*` をオペランドに持つ。**
コンパイル時に `global_cell(name)` でセルを作る（未定義でも作る）。
実行時は 1回のロードと未束縛チェックだけ。ハッシュ検索が消える。

```
struct GlobalCell { ValuePtr value;  // nullptr なら未束縛
                    ValuePtr macro;  // マクロなら変換子、それ以外は nullptr
                    GcString name; };
```

`g_globals` と `g_macros` の2表（scheme12）を**1つのセルに統合**する。
原典がシンボルのプロパティリスト1箇所に両方入れて car で見分けていたのと
同じ構造に戻る（`micro_scheme8_notes.md` §3.3）。前方参照は、未束縛のセルを
先に作っておけば自然に解決する。

#### 4.4.5 命令セット

`Op::ARGS` は**無い**（引数はスタックに積んだまま）。`Op::LDCT` も**無い**（決定7）。

| 命令 | オペランド | 動作 |
| --- | --- | --- |
| `LD` | a=フレーム番号, b=位置 | 局所変数を積む。環境を a 回辿る |
| `LDC` | p1=定数 | 定数を積む |
| `LDG` | p1=`GlobalCell*` | 大域変数を積む。未束縛ならエラー |
| `LDF` | p1=`Template*`, b=使い捨ての印 | 雛形と現在の環境からクロージャを作って積む。**b=1 なら「直後の `APP` に消費されて即座に死ぬ」印**で、VM は確保せずスクラッチを使い回す（12日目の決定54） |
| `APP` | a=引数の個数 | スタック上の `arg0 .. arg_{n-1} callee` を呼ぶ。ダンプを積む |
| `TAPP` | a=引数の個数 | 同上。ダンプを積まない（末尾呼び出し） |
| `ARGS_AP` | a=個数 | `apply` 用。末尾のリストと手前の a-1 個を1つのリストにまとめる |
| `APPLY` / `TAPPLY` | — | `apply` 用。callee と引数リストを取り出して呼ぶ |
| `RTN` | — | ダンプを1つ戻す。空なら実行終了 |
| `SEL` | p1=真の枝, p2=偽の枝 | 分岐。ダンプに戻り先を積む |
| `SELR` | p1=真の枝, p2=偽の枝 | 末尾位置の分岐。ダンプを積まない |
| `JOIN` | — | `SEL` の戻り先へ帰る |
| `POP` | — | 1つ捨てる |
| `DEF` | p1=`GlobalCell*` | 大域定義。**シンボルを残す**（§2.4） |
| `DEFM` | p1=`GlobalCell*` | マクロ定義。セルの `macro` 側に入れる |
| `LSET` | a, b | 局所変数への代入。**代入した値を残す**（§2.4） |
| `GSET` | p1=`GlobalCell*` | 大域変数への代入。同上 |
| `CALLCC` / `TCALLCC` | — | 継続を作って、積んである関数に適用する |
| `STOP` | — | 実行終了 |

**呼び出しの約束**: `APP n` の時点でスタックは下から
`... arg0 arg1 ... arg_{n-1} callee` の順（**callee が一番上**）。

> **5日目に訂正**: ここは当初「callee が先（下）」と書いていたが、
> **scheme12 は引数を左から順に評価してから最後に演算子を評価する**
> （`comp` が `for(args) comp(a); ARGS; comp(head); APP` の順に出す）。
> 評価順はスタックの順序そのものなので、callee を下にすると
> `((begin (display "f") car) (begin (display "a") '(1)))` のような式の
> 出力順が変わる。§1.4 の優先順位1（既存資産とバイト単位で同じ出力）を
> 守るため、**評価順は scheme12 のまま**にし、callee を一番上に置く。
> 引数は `[sp-1-n, sp-1)` の区間にあるので、フレームの切り出しは同じく素直。

`apply` だけは引数の個数がコンパイル時に決まらないので、`ARGS_AP` で
リストにまとめてから `APPLY` / `TAPPLY` で呼ぶ（§4.1 の「apply のときだけ
リスト化が必要」）。`APP` に動的な個数を渡す方式は、callee の評価中に
別の `apply` が走ると個数を保持する場所が壊れるので採らない。

#### 4.4.6 `Instruction` の持ち方（§9 の保留を解消）

**固定長 32 バイトの構造体。**汎用のポインタ枠を2つ持ち、意味は命令ごとに
上の表で決める（型付きのアクセサ関数を1箇所だけ用意し、キャストはそこに閉じる）。

```
struct Instruction {
    Op            op;    // 1
    std::uint16_t a, b;  // フレーム番号 / 位置 / 引数の個数
    SourcePos     pos;   // 実行時エラーに位置を添えるため（§1.4 の優先順位3）
    void*         p1;
    void*         p2;
};
```

却下案: `std::variant` / 命令種別ごとの副表。前者は最大要素に合わせて太り、
後者は逆アセンブルとトレースが2箇所を引き回すことになる。
scheme12 の 100バイト超（`std::string` + `std::vector<std::string>` +
`optional<std::string>` が常に同居）に比べれば固定長32バイトで十分小さい。

`LDF` の `Template` はコンパイル時に1個だけ作る:

```
struct Template { GcVec<GcString> params; std::optional<GcString> rest;
                  Code* body; GcString name; };
```

`LDF` の実行は「雛形と現在の環境を束ねる」だけになり、クロージャ生成のたびに
仮引数名の配列を複製しない（scheme12 は `lambda_params` を毎回コピーしていた）。

**決めたこと**

9. **値モデルは「タグ付き基底クラス + 継承」にする。**
   `Object`（tag + ソース位置、12バイト）を各型が継承し、値は `Object*` 一本。
   却下案: scheme12 の `Value{std::variant<...>}` + 実体を別確保する二段構え。
   理由: (a) cons 1個が 2回の確保・56バイトから **1回の確保・32バイト**になる。
   (b) variant は最大要素（32バイトの文字列）に合わせて全 Value が太る。
   (c) ヘッダの詰め物にソース位置がちょうど収まる（決定12）。
   なお **`nullptr` は値ではない**。空リストは必ずシングルトン `g_nil`。
   scheme12 は `is_nil(nullptr)` を真としていたが、これは「うっかり nullptr が
   混ざっても気づけない」設計なので引き継がない。

10. **小さい整数はポインタに埋め込む（即値 fixnum）。**
    最下位ビットが 1 なら整数（62bit + 符号）、0 ならヒープオブジェクト。
    `(+ acc 1)` が 1回も確保しなくなる。§4.1 のベンチが最も効く場所で、
    しかも**後から入れると算術プリミティブを全部書き直すことになる**ので今決めた。
    保守的 GC との相性: 奇数のビット列は「ヒープ内部を指すように見える」ことで
    偽 retention を起こしうるだけで、破壊は起きない。
    却下案: scheme12 どおり全整数を `BigInt` オブジェクトにする（単純だが、
    ベンチのループが毎回 2回確保する）。
    **制約**: bignum 演算の結果が fixnum に収まったら必ず fixnum に落とすこと。
    これを守らないと §2.2 の「数値は値比較」が表現によってぶれる。→ §9 に記載。

11. **プリミティブは `std::function` ではなく素の関数ポインタ
    `ValuePtr(*)(ValuePtr* argv, std::size_t argc)`。**
    理由: (a) `std::function` はキャプチャを持つと `::operator new`
    （libgccpp 経由で `GC_MALLOC_UNCOLLECTABLE`）から確保し、`gc` 継承クラスの
    デストラクタは呼ばれないので解放されない（§1.6-2 と同じ穴）。
    (b) §4.1 の「引数をスタック上に積んだまま渡す」が、そのまま
    `(argv, argc)` として書ける。scheme12 は呼び出しごとに `ValueVec` へ
    詰め替えていた。

12. **ソース位置はオブジェクトのヘッダに埋める**（§9 の保留を解消）。
    却下案: `Pair*` → `SourcePos` の副表。理由: **キーが強参照になるので、
    読み込んだペアが永久に回収されない**。これは「気づかないうちに溜まる」
    たぐいの問題で、今回いちばん避けたいもの。ヘッダ埋め込みなら、tag の後ろに
    どのみち入る詰め物に col/file/line が収まり、ペア1個あたりの増分は
    16バイト、参照はハッシュ引きでなくフィールド読み出しで済む。
    - 位置を持つのは**リーダが作ったオブジェクトだけ**。実行時に cons した
      ペアの位置は 0（＝位置なし）。
    - **アトムは位置を持たない**。シンボルはインターンされて共有されるので
      持てず、fixnum は即値でヘッダが無い。エラーは「一番近い、位置を持つ
      囲みフォーム」を指す（`nearest_pos`）。リストの各ペアには自分の car に
      あたる要素の位置を、先頭のペアには `(` の位置を入れてある。
    - ソースは全文を `g_sources` に保持する（キャレット行を描くため）。
      REPL の入力は 1 回ごとに別のソースとして登録する。同じ枠を使い回すと、
      前の入力で作られたクロージャのエラーが今の入力の行を指してしまう。
      ファイル id は 16bit なので上限 65535、超えたら位置なしに落とす。

13. **ポートのファイナライザは `make_port()` で明示登録する。**

### 2026-09-04（11日目）— マクロ展開後の位置情報（§9 の積み残し）

52. **`compile_lambda` は `comp` が解決済みの位置を受け取る。**
    - 症状: マクロが `lambda` を含むフォームへ展開すると、**その本体で
      起きたエラーが位置を丸ごと失う**。`Fatal error:` の後にファイル名も
      行番号もキャレット行も出ない
    - 原因: `comp` は `pos = nearest_pos(expr)`、無ければ `inherited` という
      二段構えで位置を決めているのに、`compile_lambda` が
      **`nearest_pos(whole)` を引き直していた**。展開が生んだ `lambda`
      フォームは位置を持たないので、そこで `inherited` が捨てられ、
      本体以下が丸ごと位置なしになる
    - 修正: `compile_lambda` に `inherited` を渡し、
      `nearest_pos(whole)` が不明なときはそれを使う。呼び出しは
      `comp` の中の2箇所（`lambda` と `(define (f ...) ...)`）で、
      どちらも解決済みの `pos` を渡せる
    - `comp_body` の空本体も `SourcePos{}` ではなく `inherited` を積むようにした
    - **これは `let` / `cond` / `do` / 名前つき `let` / 内部 define など
      「lambda に落ちる構文」すべてに効く。** ただし普通のソースでは本体の
      フォーム自身が位置を持つので、症状が出るのは展開が生んだ本体だけだった
    - **教訓: 位置の継承は鎖であって、一箇所でも `nearest_pos` を引き直すと
      そこから下が丸ごと落ちる。** `lambda` を作る場所を足すときは、
      `comp` が解決済みの `pos` を必ず渡すこと（§4.2 に追記した）

59. **dynamic-wind は「普通の道は Scheme、脱出と再入は VM」で分ける。**
    - 普通の道（`before` → `thunk` → `after`）は `lib13.scm` に書く。
      **`before` を呼んでから枠を積む**順序に意味がある。`before` 自身が
      脱出したときに `after` を呼ばせないため（R5RS もそう定めている）
    - 大域に `g_winds`（`WindEntry{before, after, id}` の配列）を置く。
      **動的エクステントは1本しかない**ので大域でよい。`id` は通し番号で、
      同じ `before`/`after` の組が入れ子で二度積まれても別枠と分かる
    - 継続は捕捉時の `g_winds` のコピーを持つ。起動時に一致しなければ、
      **出る枠の `after` を内側から、入る枠の `before` を外側から**呼んでから
      状態を差し替える
    - **巻き戻しはその場で組んだ命令列で行う**（`VM::build_rewind_code`）。
      `LDC <thunk>` `APP 0` `POP` の繰り返しに、最後の
      `LDC <値>` `LDC <継続>` `APP 1` を付けるだけ。コンパイラは通さない
    - **なぜ VM の中に置くか。** 脱出と再入は継続を起動する側にしか分からない。
      プリミティブから Scheme を呼び戻す口は `apply_callable`（VM をもう1つ
      回す）しか無く、そこで継続を捕捉すると**内側の VM だけ**を捕まえて
      しまう。だから `do_call` の継続の枝に置いた
    - 入れ子は thunk を走らせる**前**に目標へ合わせる。`after` / `before` の
      中でさらに脱出されたときに、同じ枠を二度巻き戻さないため

### 2026-09-04（15日目）— (exit) で終われるようにする

利用者から「このScheme処理系、`(exit)` で終われないようですが、これで良いのですか？」
という問いが出た。**良くなかった。** 調べると `scheme13.cpp` には `exit` という
プリミティブが1つも無く、REPL を抜ける手段は EOF（Ctrl-D）だけで、
しかも `(help)` はコマンドを9個並べておきながら**抜け方を1行も書いていなかった**。

    経緯を実機と原典で確かめた:

    | 処理系 | 終える手段 |
    | --- | --- |
    | 原典 `micro_Scheme8.lisp` | **`quit`**（`micro_Scheme8.lisp:383` で自分自身に束縛した変数。REPL の `(do ((output nil)) ((eq output 'quit)) ...)` が評価結果を見て抜ける） |
    | scheme12 | EOF のみ |
    | scheme13（14日目まで） | EOF のみ |

    scheme13 は §1.1「scheme12 と同じ振る舞いを、選び直した設計で実現する」
    のとおりに動いていた、とは言える。だが**原典にはあった**。
    しかも §1.4 の脚注のような話ではなく §1.5「デバッグ機能は一級市民」の
    ど真ん中で、`dev_memo.md` §10 には利用者自身が「`quit` で終了」と
    書いていた。**scheme12 を基準に見ている限り気づけない種類の穴**である。
    以後、原典にあった表面仕様は「scheme12 に無い」を理由に落とさない。

65. **`lib13.scm` の採用基準（決定42）を破る唯一の例外にした。**
    `exit` は R5RS に無い（R7RS 6.14）ので、基準「R5RS にあって scheme13 に
    無いもの」では拾えない。**基準の外にあるものを黙って足すのは §1.1 に
    反する**ので、利用者に諮って承認を得てから入れた。
    - **基準を緩めたのではない。** 次に R5RS 外のものを入れたくなったら、
      そのつど利用者と決めること。`lib13.scm` の冒頭にもそう書いた
    - 却下案: `system_lib.scm` に足す。既存資産なので触らない（決定42 と同じ）

66. **終了は `std::exit` ではなく専用の例外 `SchemeExit` を投げ、`main` で
    受けて普通に `return` する。** 理由が2つある。
    - **`std::exception` を継承しない。** 継承すると `try_load_library` の
      `catch (const std::exception&)`（候補を次へ送る）と REPL の
      同じ catch に飲まれ、**終了要求が「読めなかった」「エラーだった」に
      化ける**。素通りさせたいものは、素通りする型にしておく
    - `main` から普通に返れば stdio が開いている出力ポートを流して閉じる。
      §1.6 の後始末を1箇所に集められる
    - この結果、セクション2 の「処理系が投げる唯一の例外型」という
      SchemeError のコメントが嘘になったので直した

67. **R7RS の「外へ出る `dynamic-wind` の `after` を走らせてから終わる」を
    満たす。走査は Scheme 側に書く。** プリミティブから VM へ再入する経路を
    作らない方針（決定59）は継続の巻き戻しと同じ。C++ が足すのは
    `%wind-top-after`（いちばん内側の枠の `after`、無ければ `#f`）と
    `%exit`（終了コードを決めて投げる）の2つだけ。

    ```scheme
    (define exit
      (lambda args
        (let loop ()
          (let ((after (%wind-top-after)))
            (if after
                (begin (%wind-pop) (after) (loop)))))
        (%exit (if (null? args) 0 (car args)))))
    ```

    **`%wind-pop` を `(after)` より先に呼ぶ順序に意味がある。** `after` の中から
    また `exit` されたときに同じ枠を二度巻き戻さないため。
    `build_rewind_code`（セクション10）が同じ理由で同じ順序にしている。

68. **`quit` は変数ではなく手続きの別名にした。** 原典どおり「評価結果が
    シンボル `quit` なら抜ける」にすると、`(display 'quit)` のような式まで
    終了の合図になりかねない。`(quit)` と書く。**原典との差なので記録しておく。**

69. **終了コードは下位8ビットに畳む。** 親プロセスにはどのみち下位8ビットしか
    届かないので、畳んでおけば C++ 側の値と実際に観測される値が一致する。
    畳まないと `(exit 256)` が 0 になる理由を追えない。
    R7RS 6.14 に倣って 引数なし/`#t` は 0、`#f` は 1、整数はその値、
    それ以外は 0。

70. **「一度しか終われない」テストは、ゴールデンと shell の2段で見る。**
    `.scm` 1本では `exit` を一度しか呼べないので、ゴールデン

### 2026-09-06（18日目）— 浮動小数点数を入れるための仕様再検討

SICP 第1章を scheme13 で実装する実験で、実数前提の題材（平方根のニュートン法、
区間二分法、円周率の近似）をすべて整数に読み替える羽目になった
（`sicp/ch1/*.scm` の冒頭に、そう書いた注記が3箇所ある）。
利用者の判断で浮動小数点数を入れる。

**この日は設計だけで、ソースは1行も触っていない。** 実装は19日目から4日に割る
（決定95）。理由は、入れる場所が値モデル・リーダ・表示・算術・ライブラリ・文書と
全セクションにまたがり、**書き始めてからでは直しにくい決定が3つある**（決定82・85・91）
ため。ここを先に固めないと、scheme12 が陥った「少しずつ違う判断が層になる」状態を
数の側で再生産する。

80. **憲章と凍結仕様を、意図して変える。** §2.2 の「整数のみ。有理数・実数・
    複素数はない」と、`scheme13解説.md` §14.2「設計として入れないもの」から、
    **「実数」の1語だけを外す。** 有理数と複素数は入れたままにしない（決定81）。
    - §0 の「憲章を変えたくなったら」に従い、何をなぜ変えたかをここに残す。
      **黙って変えるのが最も避けたい行動**なので、§2 の冒頭にも改訂の断りを入れた
    - §1.1「scheme13 の目的は新機能ではない」との関係: **書き直しは終わっている。**
      受け入れ基準（§5.1）も性能目標（§5.3）も達成し、原典との差も総ざらいした
      （16・17日目）。**書き直しが終わった処理系に、利用者の必要で機能を足す段階に
      入った**という理解。ただし足し方は §1.1 の流儀を守る:
      層を作らない・決定を残す・退役させたものは消す（`lib13.scm` の
      「整数しか無いので」を前提にした定義は**書き換えるのであって、横に足さない**）

81. **数の塔は2階建てにする。正確な整数と、不正確な実数。**

    | 種類 | 表現 | 正確さ |
    | --- | --- | --- |
    | 整数 | 即値 fixnum / ヒープ Bignum（`cpp_int`） | 正確 |
    | 実数 | ヒープ Flonum（IEEE 754 binary64） | 不正確 |

    - **有理数を入れない**: `/` の意味をもう一度変えることになる（決定82 で
      利用者が「変えない」を選んだ時点で、入れる動機はほとんど消える）。
      加えて `7/2` の読み書き・約分・混合演算・`quotient` の作り直しが要り、
      作業量が倍以上になる
    - **複素数を入れない**: 使う当てがない。R5RS も実装しないことを許している
    - **単精度にはしない。** 原典（CL）の既定は single-float だが、SICP の題材
      （ニュートン法の収束判定、区間二分法）は倍精度でないと話にならない

82. **`/` は整数どうしなら今までどおり0方向切り捨て。実数が一つでも混ざれば
    実数除算**（3案を利用者に諮って A を選択）。

    **諮る前に「凍結仕様が本当に縛っているのか」を実測した。結果は「縛っていない」。**
    受け入れ基準の12件で `/` が現れるのは4箇所しかなく、**割り切れない整数の
    除算はそのどれでも走らない**:

    | 現れる場所 | 実際に走るか |
    | --- | --- |
    | `hashtable_lib.scm:432`（衝突率の表示） | **走らない。** ゴールデンが呼ばない関数の中 |
    | `test_fixes.scm:23`（`(/ 5)`） | **走らない。** 定義されるだけで呼ばれない内側の `lambda` の中 |
    | `test_improvements.scm:79`（`(/ 5)`） | **走らない。** これは文字列で、出るのは「手で確かめてください」という行だけ |
    | `test_improvements.scm:73-74`（`(/ 10 2)` `(/ 100 5 2)`） | 走る。**どちらも割り切れる** |

    つまり **§5.1 のバイト一致は `/` を縛っていない。** 縛っているのは設計の
    一貫性のほうである。それを承知のうえで A を選んだ。

    **ついでに分かったこと: §2.3 が凍結している `/` の2行を実際に守っているのは、
    受け入れ基準の12件ではなく scheme13 自身のテストだった。**

    | 凍結している行 | 実際の後ろ盾 |
    | --- | --- |
    | `(/ -7 2)` → `-3` | `tests/lib13_test.scm` の `(quotient -7 2)` → `-3`（`quotient` が `/` そのもの） |
    | `(/ x)` のエラー文面 | `--selftest` の `selftest_errors()`（ソースにも「§2.3 で凍結した文面。中身は変えない」と書いてある） |

    12件は「scheme12 と同じ出力を出すこと」しか見ておらず、**凍結仕様の個々の行を
    見ているわけではない。** §9 に積んだ。
    - **却下案B（割り切れなければ実数）**: 正確さが**値**で決まる。
      `(vector-ref v (/ n 2))` が n の偶奇で成否を変える。
      **R5RS が有理数で避けている落とし穴を、有理数無しで踏むことになる**
    - **却下案C（有理数も入れて数の塔を完成させる）**: 決定81
    - **引き受ける代償**: `(/ 1 3)` は `0` のまま。SICP を写すときは `1.0` か
      `exact->inexact` を意識する必要がある。**仕様であって不具合ではない**ので、
      `(help)` と `scheme13解説.md` に明記する
    - `(/ x)` は引数の型によらずエラーのまま。**型で arity が変わる規則は作らない。**
      既存の文面「use (/ 1 x) instead」は実数でも正しい助言になる（`(/ 1 2.0)` → `0.5`）

83. **原典（CL の数値塔）には合わせない。** これまでの復活案件
    （`test-start`/`test-end`・`quit`・`macro-print`）は「原典にあって scheme12 が
    落としたもの」だったので、名前も返り値も原典に合わせた（決定29・65・77）。
    **今回は性質が違う。**
    - 原典の数は CL の数値塔そのもので、有理数つき・既定 single-float。
      scheme12 がそこを捨てて整数だけにし、**既存資産12件はその上に書かれている。**
      いま原典に戻すのは互換性を壊す方向の変更で、復活ではない
    - したがって入れるのは **R5RS の「不正確な実数」**。綴りは R5RS と、
      R5RS に無いもの（`+inf.0` など）は R7RS に合わせる
    - `micro_scheme8_notes.md` §5 の「CL の数値塔（有理数）→ 整数のみ」の行は、
      実装後に「→ 整数と倍精度実数」に直す。**有理数の差は残る**

84. **表現はヒープ上の `Flonum`。即値にはしない。**
    - 64ビットの double は、最下位1ビットをタグに使う即値方式（決定10）に入らない
    - **却下案: NaN ボクシングで値表現ごと作り直す。** `ValuePtr` を触る全コードに
      波及し、§1.1（目的は統一であって作り直しではない）に正面から反する。
      得られるのは実数の確保削減だけで、**既存の整数の速い道は今のままで十分速い**
    - `Flonum` はポインタを持たないので **`new (PointerFreeGC) Flonum(v)` で確保する。**
      §1.6-4 の `GC_DECLARE_PTRFREE(unsigned long long)` と同じ趣旨で、
      double のビット列がヒープへの偽 retention を起こさないようにする
    - **実測で確かめた**（`/usr/include/gc/gc_cpp.h`）。`PointerFreeGC` は
      `GCPlacement` の値として存在し、`gc` を継承したクラスに
      `operator new(size_t, GCPlacement)` が生えている。scheme13 と同じ形の
      `Object`（仮想関数なし）+ `Flonum` を書いて、**`sizeof(Flonum)` が
      ちょうど24バイト**、20万個確保して `GC_gcollect()` しても壊れないことを確認した。
      ビルドは clang++ なので、そちらでも通ることだけ19日目に見ること
    - ヘッダ12バイト + double 8バイト = **24バイト**（実測）。**`Flonum` は
      ヘッダを持つので、リーダが位置を貼れる**（fixnum は即値なので貼れない）。
      §2 の非対称がここで一つ埋まる

85. **正確さは値の一部。実数の結果を整数に落とさない。**
    §9 の「bignum の結果が fixnum に収まったら必ず fixnum に落とす」の**裏返し**の規律。
    - `(* 2.0 3.0)` は `6.0` であって `6` ではない。`(floor 2.5)` は `2.0` であって `2` ではない
    - 破ると `exact?` の答えが値で変わり、`eqv?` の結果も変わる
    - **整数側は「同じ数は同じ表現へ正規化する」、実数側は「正確さをまたいで
      正規化しない」。向きが逆である。** `make_int` の感覚で `make_flonum` を書くと
      必ず間違える。§9 に2つ並べて書いた

86. **`eqv?` は正確さが一致して初めて真。`=` は数として比べる。**
    - `(= 1 1.0)` → `TRUE`、`(eqv? 1 1.0)` → `FALSE`（R5RS どおり）
    - 実数どうしの `eqv?` は**ビット列で比べる**。帰結:
      `(eqv? 0.0 -0.0)` → `FALSE`、`(eqv? +nan.0 +nan.0)` → `TRUE`。
      `=` は逆に `(= 0.0 -0.0)` → `TRUE`、`(= +nan.0 +nan.0)` → `FALSE`
    - **これは §2.2「数値は値比較」の拡張であって変更ではない。** 実数が存在しなかった
      ので、整数どうしの振る舞いは1つも動かない
    - `equal?` は数について `eqv?` と同じにする（R5RS）。いまは `num_cmp(...) == 0` を
      使っているので `eqv_number()` に差し替える。**bignum どうしは値で比べ続けること**
      （ポインタが違うため。`(equal? 100000000000 100000000000)` → `TRUE` を壊さない）
    - `case` / `memv` / `assv` はこの `eqv?` に乗る。`(case 1.0 ((1) ...))` は当たらない

87. **NaN があるので、比較は3値では足りない。** これは実装の都合ではなく仕様である。
    - いまの `num_cmp` は -1 / 0 / 1 を返し、`DEFINE_NUM_CMP` が `c == 0` / `c < 0` /
      `c <= 0` などで判定している。**NaN は「どの比較も偽」でなければならないが、
      `c == 0` と `c < 0` と `c > 0` を同時に偽にする整数は存在しない**
    - したがって `num_cmp` は **4状態（`LT` / `EQ` / `GT` / `UNORDERED`）**を返す形にし、
      判定を列挙の突き合わせに書き換える。`<=` は `LT || EQ`。
      **「`<` の否定」で書かないこと**（NaN でひっくり返る）

88. **混合比較は倍精度に寄せる。桁が落ちることを仕様として書く。**
    - `=` `<` などで整数と実数が混ざったら、整数を double にして比べる
    - 2^53 を超える整数は double に正確に載らないので、その近傍で答えが数学的な真と
      ずれうる。**正確に比べるには有理数が要る**以上（決定81）、**ずれることを
      §2.3 に書いておく**のが誠実な扱い
    - **却下案: bignum と double を厳密に比較する。** 数十行で書けるが、`=` の
      ホットパスに分岐が増える。この処理系で 2^53 超の混合比較を書く人がいるとは
      考えにくい。必要になったら入れる

89. **リーダは「自前で判定してから数に変える」。`std::from_chars` に判定させない。**
    - いま `1.5` は**シンボル**として読まれる（実測: `unbound variable: 1.5`）。
      **実数に見えるトークンは、受け入れ基準の12件にも `lib13.scm` にも
      `tests/*.scm` にも1つも無い**（コメントと文字列を落として全走査した。
      走査式は決定61 の流儀で `micro_scheme8_notes.md` §8 に置いた）。
      **したがって、ここを数にしても既存の出力は1バイトも動かない**
    - **`from_chars` に判定を任せてはいけない。実測で確かめた。**
      `+inf.0` だけ手前で分岐して残りを `from_chars` に渡す骨組みを書いて流すと、
      **`inf` / `nan` / `infinity` の3つが数に化けた**（`1/2` `1e` `1.2.3` `...`
      `-` `+` は化けない）。**自前の走査で「数である」と決めてから、変換にだけ
      `from_chars` を使う。** いまの `read_atom` が桁を自前で見ているのと同じ流儀
      （文法は §2.5 に書いた）
    - **`string->number` はリーダと同じ判定を使う。** 数の文法を2つ持たない

90. **表示は「読み戻せる最短形」。`to_chars` の shortest に後処理を1つかける。**
    - `std::to_chars(double)`（shortest round-trip）を使う。**この容器の g++ 15.2 /
      libstdc++ で動くことを実測した。** ビルドは clang++ なので実装時に再確認する
    - そのままでは Scheme の形になっていないので、4つだけ直す:

      | `to_chars` | scheme13 | 直し方 |
      | --- | --- | --- |
      | `1` | `1.0` | `.` も `e` も無ければ `.0` を足す |
      | `1e+21` | `1e21` | 指数の `+` を落とす |
      | `1e-07` | `1e-7` | 指数の先頭の 0 を落とす |
      | `-0` | `-0.0` | 上の1つ目と同じ規則で足りる |

      無限大と NaN は `to_chars` に渡す前に分岐して `+inf.0` / `-inf.0` / `+nan.0` を出す
    - **`(+ 0.1 0.2)` は `0.30000000000000004` と出る。丸めて隠さない。**
      §1.5（デバッグ機能は一級市民）に照らせば、**見えている数がメモリにある数で
      あること**のほうが大事。§2.1 の注記のとおり scheme13 の `write` は読み戻せない
      出力（`NIL` など）を含むが、**数についてはここで初めて読み戻せるようになる**
    - **却下案: `%.15g` のような固定桁で「きれいに」出す。** `(+ 0.1 0.2)` が `0.3` に
      見えるのに `(= (+ 0.1 0.2) 0.3)` が `FALSE`、という**最悪の組み合わせ**になる
    - `number->string` は `write` と**同じ関数**で作る。書式を2つ持たない
    - **§2.1 の表は実装前に検算してある。** この規則をそのまま書いた30行の
      C++ に上の表の式を流し、**9行すべてが表のとおりに出ること**を確かめた。
      さらに正規数・非正規数・両端（`4.9e-324` と `1.7976931348623157e308`）を
      含む18個で**書いて読み戻すとビット列が一致すること**を確かめた（0件失敗）。
      **検算の程度は「上の表の4つの後処理をそのまま書く」だけ**なので、
      疑わしくなったら30行で測り直せる。`tests/` に検算用のソースは置いていない
      （動かない足場を残さない。§1.1）

91. **伝播規則は「一つでも不正確なら結果は不正確」。整数の速い道は触らない。**
    - `+` `-` `*` はいま2段（全部 fixnum なら fixnum のまま回す / 溢れるか fixnum で
      ない値に当たったら bignum の道）。ここに**3段目を足すのではなく、落ちた先で
      1度だけ「不正確が混ざるか」を見る**:
      1. 全部 fixnum → いままでどおり（**1命令も増やさない**）
      2. 落ちた → 残りを走査し、実数が1つでもあれば double の道、無ければ bignum の道
    - `num_cmp` も同じ形。fixnum どうしの分岐を先頭に残す
    - §1.4-2 に照らし、**整数だけのプログラムの速度が落ちないことを実装の受け入れ
      条件にする。** `make bench` と赤黒木4万件（決定57 の測り方）で前後を測る

92. **整数を要求する場所は、実数を黙って受け取らない。**
    - 添字・長さ・文字コード・乱数の上限などはすべて `num_of` / `ll_of` を通っている

      **新しい検査を足す必要は無い**が、仕様として §2.3 に書き、`--selftest` に項目を置く
    - `modulo` / `quotient` / `remainder` / `even?` / `odd?` も**正確な整数だけ**を受ける
    - **却下案: 整数値の実数（`2.0`）を許して不正確な結果を返す。** R5RS はそれを
      許すが、**「整数を要求する場所」の規則が場所ごとに違うことになる。**
      添字は弾いて剰余は通す、という線は説明できない。必要になったら利用者に諮る

    **そのままでは全部おかしくなる。** 書き換える対象と行き先:

    | `exact?` `inexact?` | 数なら常に正確（lib13） | **C++**。表現を見る |
    | `exact->inexact` `inexact->exact` | 無い | **C++**。`inexact->exact` は**整数値でない実数をエラー**にする（有理数が無いので近い正確な数を作れない） |

### 2026-09-06（20日目）— 実数で計算できるようにする

18日目の計画（決定95）の2日目。**伝播規則・比較・正確さの述語と変換**を入れた。

101. **整数から実数への変換は `to_double()` の1箇所に閉じた。**
     - fixnum / Bignum / Flonum の3つを受け、それ以外は
       `expected: a number` で弾く

     - 走査は1回のまま。**速い道（全部 fixnum）はこの関数を呼ばない**ので、
       整数だけのプログラムには1命令も増えない（決定91）
     - 却下案: `num_of` の隣に「a number」と言う双子を作る。
       **同じことをする関数が2つになる**（§1.1）。呼ぶ前に弾くほうが1つで済む
     - 回帰は `selftest_errors` の "arithmetic type error"

103. **丸め4つ（`floor` / `ceiling` / `truncate` / `round`）を21日目から前倒しした。**

105. **定義域の外でも例外にしない。IEEE 754 に従う。**
     - `(log 0)` → `-inf.0`、`(log -1)` → `+nan.0`、`(asin 2)` → `+nan.0`
     - §2.3 で `(/ 1.0 0.0)` を `+inf.0` にすると決めたのと同じ扱い。
       **実数の演算で例外を投げる場所を1つも作らない**という線を引いた
     - **例外は `sqrt` の負の引数だけ**（決定106）。あれは「表せない」ので別扱い

106. **`sqrt` と `expt` は「正確な道を先に試す」。順序が仕様である。**
     - `sqrt`: 引数が正確なら**まず平方根の整数部を求め、二乗して元に戻れば
       その整数を返す**。戻らなければ `%sqrt` で実数。
       **判定に使うのは、これまで「平方根の整数部」を返していたニュートン法
       そのもの**（`%isqrt` として括り出した）。整数の割り算で回るので
       多倍長でも正確で、`(sqrt 9999999999800000000001)` は `99999999999` のまま
     - `expt`: 底も指数も正確で指数が0以上なら繰り返し二乗、それ以外は `%expt`。
       **先に `%expt` へ渡すと `(expt 2 100)` が倍精度に丸まる。** 順序を逆にすると
       静かに桁が落ちるので、`lib13.scm` にその旨を書いた
     - **`sqrt` の負の引数はエラーのまま。** 実数を入れても答えは虚数のままで、
       表せないものは表せない。`+nan.0` を返すと「数でない」と嘘をつくことになる。
       却下案: 他の多くの Scheme に倣って `+nan.0` を返す。**嘘の種類が違う**
     - 実測: `(sqrt 2)` → `1.4142135623730951`、`(sqrt 16)` → `4`、
       `(sqrt 17)` → `4.123105625617661`、`(expt 2 -3)` → `0.125`、
       `(expt 2.0 3)` → `8.0`、`(expt 2 100)` → 正確な多倍長

107. **ゴールデンに libm の最後の桁を載せない。**
     `tests/lib13_test.scm` はゴールデンとバイト単位で比べられる。ここに
     `(exp 1)` → `2.718281828459045` のような値を書くと、**移植先で libm が
     変われば落ちる**（root の Makefile は FreeBSD / NetBSD / MinGW も想定している）。
     - 固定してよいもの: **正確に表せる値**（`(exp 0)` → `1.0`、`(sin 0)` → `0.0`、
       `(log 0)` → `-inf.0`、`(asin 2)` → `+nan.0`）と、
       **IEEE 754 が正しい丸めを義務づけている `sqrt`**
     - それ以外は**誤差の範囲で見る形**にした:
       `(< (abs (- (* 4 (atan 1)) 3.141592653589793)) 1e-15)` → `TRUE`
     - 同じ理由で `--selftest` にも `(exp 1)` の値そのものは置いていない
     - **これは「テストを甘くした」のではない。** 何が処理系の責任で、何が
       libm の責任かを分けただけである

108. **`max` / `min` は「選ぶこと」と「不正確さを伝えること」を分けて畳む。**
     R5RS は「引数に不正確が1つでもあれば結果も不正確」と決めているので、
     `(max 2 1.0)` は `2` ではなく `2.0`。
     - 畳み込みの状態を2つ（いまの最大値と、不正確を見たか）持ち、
       **最後に1度だけ `exact->inexact` する**
     - 却下案: 比べるたびに `exact->inexact` を挟む。**選ばれなかった側の
       不正確さが消える。** `(max 2 1.0)` で 1.0 が捨てられた瞬間に、
       「不正確な引数があった」という事実まで捨ててしまう

## 9. 保留・未解決の問い

- ~~**ソース位置の持たせ方**~~ → 3日目の決定12 で解決（ヘッダに埋め込む）。

- **テストが「開発側の想定した使い方」しか通っていないのではないか**
  （15日目の帰結）。`(exit)` が無いことに14日間気づかなかったのは、
  `selftest` も `run_golden.sh` も**式を評価させることしか見ていない**ため。
  REPL を人が触る筋道（起動する・打つ・抜ける・`(help)` を読む）は
  どのテストも通っていない。
  → 15日目に終了コード5件だけは shell 側で見るようにした（決定70）。
  残りをどこまで自動化するかは未決。**急がないが、忘れないこと。**

- **数の2つの規律。向きが逆なので、必ず並べて読むこと**（決定10 と決定85 の帰結）。

  **(1) 整数側 — 同じ数は同じ表現へ正規化する**
  - fixnum どうしの演算は `__builtin_*_overflow` で検査し、溢れたら bignum へ
  - **bignum 演算の結果が fixnum に収まったら必ず fixnum に落とす**
    （`make_int(const BigInt&)` が既にそうしている。専用の経路を増やさないこと）
  - これを破ると §2.2「数値は値比較」が表現によってぶれ、`eq?` の結果が変わる
  → `--selftest` の `selftest_eval` に境界のテストを入れてある（"fixnum overflow"
    と "normalize back"）。算術を触ったら必ず通すこと。
  → この帰結として `memq` / `assq` は scheme12 と結果が違う（決定28）。

  **(2) 実数側 — 正確さをまたいで正規化しない**（18日目の決定85。**実装は19日目から**）
  - `(* 2.0 3.0)` は `6.0`。整数に落とさない
  - 破ると `exact?` が値で変わり、`eqv?` の結果も変わる
  - **「正規化する」という語が、整数では正しく実数では間違い。**
    `make_int` の感覚で `make_flonum` を書かないこと

- **凍結仕様の各行が、どのテストで守られているのか誰も測っていない**
  （18日目の帰結。決定82）。`/` について測ったら、こうだった:
  - §2.3 の2行（切り捨てと `(/ x)` のエラー文面）を実際に守っていたのは、
    受け入れ基準の12件では**なく**、`tests/lib13_test.scm` と `selftest_errors()`
  - 12件のほうは `/` を4箇所に持っているが、**割り切れない除算はどれも走らない**
    （呼ばれない `lambda` の中・文字列・割り切れる式）
  - **受け入れ基準は「scheme12 と同じ出力を出すこと」を見ているのであって、
    §2 の個々の行を見ているのではない。** ここを取り違えていた
  **§2 の他の行も同じ状態のはずである。** 下の「テストが開発側の想定した使い方
  しか通っていないのではないか」と根が同じ。
  → 測り方は決まっている（該当する式を12件から grep し、**実際に走る経路かどうかまで
  見る**。grep で見つかっただけでは走っている証拠にならない、というのが今回の教訓）。
  **急がないが、§2 を次に触るときは、その行の後ろ盾を先に確かめること。**

- **混合比較の桁落ち**（18日目の決定88）。2^53 を超える整数と実数の比較は
  倍精度に寄せるので、数学的な真とずれうる。厳密比較は数十行で書けるが `=` の
  ホットパスに分岐が増える。**必要になったら入れる。**
